## 验收条件

1. 通过正常 approve 入口核对 direct_human 与 standing_delegation、未设置来源的旧记录、非法来源以及相同申请重试；批准权限与版本绑定保持原语义。
2. 临时 Git 仓库的子目录中，两个 Hook 根据真实 Git 范围和当前仓库 schema 选择唯一活动任务；显式任务、损坏、歧义、旧记录空 subject、观察原件和过期绑定均遵守既有通过/拒绝语义。对外观察仍校验必填 subject。
3. 单次和批量的契约校验按完整根及引用 schema 内容在有界范围内复用；同尺寸同时间而字节变化可影响下一次结果；批量漂移仍报告。新进程的普通核心导入不启动 Node/installed 组件；共享审批、读取、路径及状态接口保留消费者行为和封闭 mutation 握手；SDK 只读 Git 保留环境并禁用可选锁。
4. required check 根据目标分支模式、PR 三点差异和真实任务身份区分普通维护、独立关闭及正式候选。覆盖增删/重命名、多任务歧义、保留失败尝试、多个合法关闭与合法混合提交；从 Git 快照核实关闭原先获准、merge 及 incoming parent/subject，检查只追加事件。无任务的治理变更以及任务创建前已有的额外贡献（含后续更名）需要明确拒绝。
5. 本任务从当前目标基线原生 start，再引入核心与 CI 变更。以目标 main、实际当前分支和当前 head 调用真实路由入口，本集成提交应识别为 TASK-0160 的正式实施。PR 仅包含本任务账本和其两组范围内的业务变更。
6. 所有路径保留完整测试、85% 核心总覆盖率、针对真实 PR 基线的 90% diff coverage、whitespace、Ruff、format、mypy。正式 V1/V2 在同一候选重用本次完整测试产生的数据库，其他模式也满足质量门。按新任务真实分类独立审核、verify 和 Gate，主代理随后核实仓库/分支后非强推、开 PR，在当前 head required check 通过并符合目标规则后使用 merge commit。

## 禁止动作

禁止改写已推送历史、强推、直接推 main、恢复旧评分或宿主/外仓接入、数据删除、部署、凭据导出、付费调用，禁止更改授权/分支保护/质量阈值。旧 #169/#171 及其原始成功、失败和过期结论分别保留。

## 错误行为

不合法绑定、模式、旧关闭原件、候选任务、贡献来源或范围均按原生错误通道拒绝。出现新的主线基线或外部副作用时，以实际 Gate 与 required check 判断新鲜度，旧审核与结果不代替新证据。未通过的候选保留原记录。

## 回滚

使用独立分支与可追溯的前向提交；如需撤回，按后继治理任务恢复本规格覆盖的实现并保留历史、原件和原分支。
