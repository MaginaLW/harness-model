# AI 代码协同系统阶段一 MVP 实施设计

> 日期：2026-08-01
> 状态：设计方向已确认，已完成独立审阅
> 依据：`docs/architecture/AI代码协同分流与模型路由设计_V0.1.md`、`docs/architecture/AI代码协同系统实施总体规划_V0.2.md`

## 1. 文档目的

本文将现有概念设计和总体规划收敛为下一步可实施的系统设计。它定义：

- 四阶段建设路线；
- 阶段一最小闭环的技术边界；
- 七个顺序实施章节；
- 每章的任务组成、交付物、依赖和退出条件；
- 阶段一的统一验收方式；
- 阶段二至四的进入条件和里程碑。

本文负责定义“建成什么以及如何分层建设”。逐文件、逐命令、逐测试的执行清单将在设计获批后另行写入实施计划。

## 2. 当前状态与范围判断

仓库当前只有两份架构文档，没有工程骨架、可执行代码、测试、Policy、任务样例或 CI。现有 V0.2 已定义四个阶段，但阶段一仍停留在组件清单层级，尚缺少：

- 组件之间的实现顺序和依赖；
- 稳定的数据契约和命令接口；
- 章节级交付物和退出条件；
- 可重复的黄金样例；
- 子任务级验证标准；
- 从本地流程到 CI 门禁的端到端验收方法。

本轮采用以下范围：

1. 四个阶段均保留在总路线图中；
2. 只把阶段一拆到可直接实施和验收的粒度；
3. 阶段二至四仅定义进入条件、里程碑和退出条件；
4. 阶段一完成并经过真实试点后，再展开阶段二实施计划。

## 3. 方案选择

### 3.1 采用方案：纵向闭环拆分

阶段一按以下顺序建设：

```text
工程基线与可执行契约
→ 任务记录与状态核心
→ 分流与验证等级引擎
→ 治理交互流程
→ 验证与证据闭环
→ Agent 与 CI 集成
→ 试点验收与阶段一基线
```

每章必须产生可独立检查的增量，并以前一章的稳定产物作为输入。AUTO、ASK、REVIEW 和 BLOCK 黄金样例贯穿所有章节，用于防止模块分别正确但端到端流程无法运行。

### 3.2 未采用方案

**纯组件拆分**会先后完成模板、规则引擎、状态机、证据和 CI，局部边界清楚，但完整闭环出现较晚，集成风险暴露过迟。

**纯人工流程原型**可以快速验证概念，但程序契约和强制门禁会推迟，后续需要重复改造。

本设计吸收人工原型的优点：在第一章建立黄金样例和预期结果，但后续始终以可执行契约和程序门禁为主。

## 4. 阶段一目标与边界

### 4.1 目标

在本仓库中交付一个可安装、可测试、可审计的 Python CLI 最小闭环，使一个代码任务能够完成：

```text
创建任务
→ 拆解决策单元
→ 确定 AUTO / ASK / REVIEW / BLOCK
→ 独立确定 V0 / V1
→ 完成 ASK 或必要批准
→ 执行验证
→ 生成版本绑定证据
→ 由本地和 CI 使用同一规则判断是否放行
```

阶段一需要证明治理模型能够工作，不追求自动调度多个真实模型。

### 4.2 阶段一明确不做

- 不调用真实模型 API；
- 不实现复杂连续风险评分、概率模型或阈值学习；
- 不自动更新模型能力和信任度；
- 不实现 V2、V3、全仓库变异测试或高成本故障注入；
- 不实现供应商无关的多模型编排；
- 不自动执行合并、推送、部署、删除或其他高风险外部动作；
- 不实现完整 Web 审批界面；
- 不实现跨机器、多仓库并发状态同步；
- 不在多个平台适配层中复制 Policy 逻辑。

## 5. 核心设计原则

1. **程序裁决，模型辅助。** 模型或 Agent 负责理解任务、生成候选选项和审核材料；程序负责结构校验、规则计算、状态转换和质量门禁。
2. **Policy 是单一规则来源。** CLI、Skill、Hooks 和 CI 不各自维护分流规则。
3. **分流单位是决策单元。** 每个决策单元独立分类；任务级展示值只是未完成单元的安全汇总，不覆盖单元结论。
4. **分流与验证独立。** `route` 决定谁拥有决策权，`verification_level` 决定需要什么证据。
5. **只允许自动升级。** Agent 可以升级分流或验证等级；降低等级必须通过显式重新分类和授权记录。
6. **默认保守失败。** 配置缺失、规则冲突、证据不完整或版本不匹配时，不得默认为通过。
7. **版本强绑定且避免自引用。** 规格、批准、Policy 和证据均绑定被审代码的 `subject_commit`。后续只包含当前任务治理记录的 attestation commit 不改变被审代码版本；任何治理目录之外的变化，或规格、Policy 摘要变化，都会使代码批准和证据失效。CI 在 PR 最新 HEAD 重新生成权威证据，从而同时绑定被审代码和最新 attestation HEAD。
8. **适配层保持轻薄。** Agent 文件、Skill、Hooks 和 CI 只调用核心程序，不重新实现状态机或规则引擎。
9. **先以样例固定语义。** 每项核心行为先在黄金样例中写明预期，再实现规则和命令。
10. **章节顺序受退出条件约束。** 前一章退出条件未满足，不进入下一章。

## 6. 技术基线与建议结构

### 6.1 技术基线

- Python 最低版本：3.11；
- 工程布局：`src` layout；
- 命令入口：`aiflow` 和 `python -m aiflow`；
- Policy 与任务主记录：YAML；
- 分类、批准和证据等机器结果：JSON；
- 审计事件：追加式 JSON Lines；
- 测试：pytest；
- 变更覆盖：pytest-cov 在当前任务日志目录或 CI 临时目录生成分支覆盖数据与 XML，diff-cover 对 `base_commit..subject_commit` 的变更行执行不低于 90% 的门槛；覆盖产物不得写到仓库普通业务路径；
- 静态质量检查：Ruff 和类型检查；
- CI：GitHub Actions；
- 依赖版本：在第一章通过项目锁定机制固定，CI 使用同一依赖集合。

## 7. 核心接口

### 7.1 CLI 命令

阶段一提供以下命令：

| 命令 | 职责 |
|---|---|
| `aiflow start` | 创建任务、记录 Git 上下文和初始范围 |
| `aiflow classify` | 校验决策单元、执行规则并保存分流结果 |
| `aiflow freeze` | 校验并冻结当前规格，保存规格摘要但不隐式批准 |
| `aiflow answer` | 保存 ASK 选择并冻结相关规格 |
| `aiflow approve` | 保存规格、代码或真实动作批准 |
| `aiflow begin` | 在前置条件满足后记录实现或失败重试的开始 |
| `aiflow escalate` | 记录升级原因并重新进入安全状态 |
| `aiflow verify` | 解析 V0/V1 计划、运行检查并生成本地或 CI 证据 |
| `aiflow status` | 展示当前状态、缺失条件和证据新鲜度 |
| `aiflow gate` | 为本地门禁和 CI 输出确定性的放行结论 |
| `aiflow close` | 在外部合并完成后记录合并结果，不主动执行合并 |

所有改变任务状态的命令必须先读取任务记录和事件日志，校验当前状态，再以原子方式写入新记录和追加事件。

### 7.2 单个任务的持久化结构

```text
.ai/tasks/TASK-0001/
├─ task.yaml
├─ classification.json
├─ events.jsonl
├─ decisions.md
├─ spec.md
├─ review-package.md
├─ approvals.json
├─ evidence.json
└─ logs/
```

`task.yaml` 保存当前物化状态、稳定 `repository_id`、`base_commit` 和被审代码 `subject_commit`；绝对工作区路径只作本次运行诊断，不参与身份或版本绑定。`events.jsonl` 保存不可省略的状态变化历史。门禁需要验证事件重放结果与 `task.yaml` 一致，从而发现绕过 CLI 直接修改状态的情况。

本地验证产生的 `evidence.json` 和批准记录可以在 `subject_commit` 之后形成 attestation commit。Gate 只允许 `subject_commit..HEAD` 修改当前任务的 `.ai/tasks/TASK-xxxx/**`；出现其他路径即视为被审代码变化并使旧证据和代码批准失效。CI 不信任仓库内证据作为最终裁决，而是在 PR 最新 HEAD 的临时目录重新运行验证并生成权威 evidence artifact。

### 7.3 状态机

阶段一使用以下主路径：

```text
NEW
→ CLASSIFIED
→ WAITING_FOR_ASK / WAITING_FOR_SPEC_REVIEW / READY_TO_IMPLEMENT / BLOCKED
→ IMPLEMENTING
→ VERIFYING
→ VERIFIED / FAILED / ESCALATED / BLOCKED
→ WAITING_FOR_FINAL_REVIEW / APPROVED_FOR_MERGE
→ APPROVED_FOR_MERGE
→ MERGED
```

具体约束：

- ASK 回答后才能进入 `READY_TO_IMPLEMENT`；
- 需要规格审核的 REVIEW 在批准前不能实现；
- `aiflow freeze` 校验并冻结规格但不改变审批状态；`aiflow answer` 在保存 ASK 选择后原子冻结更新后的规格；
- `aiflow begin` 只允许把满足前置条件的任务转为 `IMPLEMENTING`；
- 验证成功先记录 `VERIFIED`；仅包含无需最终 REVIEW 的 AUTO/ASK 单元时，`aiflow verify` 随后自动转入 `APPROVED_FOR_MERGE`；
- 任一未完成决策单元需要最终 REVIEW 时，`aiflow verify` 在记录 `VERIFIED` 后自动转入 `WAITING_FOR_FINAL_REVIEW`，有效 `code` 批准再转入 `APPROVED_FOR_MERGE`；
- `FAILED` 只有通过带重试理由的 `aiflow begin` 才能重新实现，若失败暴露新风险则必须升级；
- `ESCALATED` 和 `BLOCKED` 只有在记录升级或阻断条件处理结果后才能重新分类；
- `aiflow close` 只记录外部已经完成的合并及合并 commit，CLI 不主动执行合并。

## 8. 分流与验证设计

### 8.1 决策单元分类

每个决策单元至少包含：

- 稳定 ID；
- 具体目标；
- 输入和计划动作；
- 影响文件或系统范围；
- 可逆性；
- 可执行验证方式；
- 外部副作用；
- 权限要求。

规则采用确定性、有优先级的表驱动方式，不在阶段一计算连续风险分数。多个规则命中时，安全优先级为：

```text
BLOCK > REVIEW > ASK > AUTO
```

每个结果必须保存：

- 命中的规则编号；
- 规则解释；
- Policy 版本和内容摘要；
- 分类输入摘要；
- 生成时间。

任务级分流只用于展示和门禁汇总，取所有未完成决策单元中的最高安全级别。它不改变任何决策单元的原始分类。

### 8.2 验证等级

阶段一仅实现 V0 和 V1：

- V0：契约校验、范围检查、语法或格式检查、Lint、Smoke Test；
- V1：V0，加单元测试、回归测试、类型检查和变更覆盖检查。阶段一使用 pytest-cov 把分支覆盖数据与 XML 写入 `.ai/tasks/TASK-xxxx/logs/<run-id>/`；CI 写入 runner 临时目录。diff-cover 检查 `base_commit..subject_commit` 的变更行，最低门槛为 90%；状态机、路由、批准失效和 Gate 决策表仍需逐行测试，不能用覆盖率替代。

Policy 为每项检查定义命令参数、超时、是否必需和结果解析方式。必需工具或命令缺失时验证失败，不得静默跳过。

## 9. 治理交互设计

### 9.1 AUTO

AUTO 在实现或验证前执行预检：

- 当前状态允许继续；
- 修改范围在允许列表内且不在禁止列表内；
- 动作未触发高风险权限；
- V0/V1 验证计划完整；
- 当前分流和 Policy 未过期。

AUTO 表示无需逐项人工决策，不表示允许外部高风险动作。

### 9.2 ASK

Agent 或 Skill 负责生成选项，CLI 负责结构校验和记录。ASK 记录必须包含 2—4 个选项；每项均包含：

- 稳定选项 ID；
- 方案说明；
- 收益；
- 代价；
- 风险。

最多一个选项可标为推荐项。CLI 可以验证结构和数量，Skill 负责要求选项在语义上实质不同。用户选择后，`aiflow answer` 把选择、操作者、时间和理由写入决定记录，并将相关内容冻结到规格。

### 9.3 REVIEW

阶段一支持三种互相独立的批准：

- `spec`：批准目标、范围和实现方向；
- `code`：批准当前被审 `subject_commit` 的实现；
- `action`：批准一次具体的真实外部动作。

审核包必须包含审核目标、背景、代码地图、语义变更、风险、证据、明确审核问题和推荐结论。批准记录绑定任务、规格摘要、Policy 摘要、commit、批准类型、操作者和时间。

代码批准不等于动作批准。阶段一不主动执行需要动作批准的行为，只记录批准结果并提供门禁判断。

### 9.4 BLOCK 与 ESCALATE

BLOCK 必须记录缺失的信息、权限或保护条件。条件解除后重新分类，不直接改写为较低等级。

ESCALATE 保存触发信号、原等级、新等级、影响范围、下一步和已有成果处理方式。除提高 route 外，规格或 Policy 变化也允许以 `policy_changed` 等具名原因执行 REVIEW→REVIEW 的同级失效升级，使任务进入 ESCALATED 后重新分类；Agent 可以执行升级和同级失效重评，不能自行降低等级。

## 10. 验证、证据和失效

### 10.1 验证执行器

`aiflow verify` 调用统一验证执行器。执行器：

- 使用参数数组运行子进程，避免拼接 Shell 命令；
- 为每项检查应用超时；
- 保存退出码、耗时、工具版本和输出摘要；
- 将完整日志保存在任务目录的 `logs/`；
- 把 `.coverage` 和 coverage XML 放在同一运行日志目录；CI 改放 runner 临时目录，不在仓库根目录生成覆盖产物；
- 对日志进行基础敏感信息过滤；
- 任一必需检查失败时返回失败。

本地最终验证要求开始运行时除当前任务治理记录外没有未提交变化，并把当前被审代码 commit 记为 `subject_commit`。`aiflow verify --ci --ci-run-dir <validated-temp-dir> --output <path-within-run-dir>` 在经验证的 CI 或本地系统临时目录重新运行同一计划，绑定观测 HEAD 和 `subject_commit`，不修改仓库内任务状态或事件；`aiflow gate --evidence <path>` 使用该权威重验证据。需要长期保存时，在验证与 Gate 完成后把脱敏 artifact 复制到持久位置。

`tools/gauntlet.py` 是兼容总体规划所述统一入口的薄包装，不复制验证逻辑。

### 10.2 `evidence.json`

证据至少包含：

- 任务和决策单元 ID；
- 稳定仓库 ID、分支、基础 commit 和被审代码 `subject_commit`；
- CI 证据额外记录 PR 最新 `attestation_head`，并证明 `subject_commit..attestation_head` 只有当前任务治理记录；
- 规格摘要和 Policy 摘要；
- 验证等级；
- 每项检查的命令摘要、工具版本、结果和日志引用；
- 未验证场景；
- 总体结论和生成时间；
- 一条可重复执行的统一命令。

### 10.3 失效规则

阶段一采用保守且无自引用的一致性规则：

- `subject_commit` 之后出现当前任务治理目录以外的变化，旧 `code` 批准和旧证据失效；
- 只新增或更新当前任务的 evidence、approval、event 等治理记录，不改变 `subject_commit`，但 CI 必须在最新 attestation HEAD 重新验证；
- 规格变化，规格批准、代码批准和证据失效；
- 会影响判定的 Policy 变化，分类、批准和证据均需重新计算；
- 任务范围扩大，重新分类；
- 新增依赖、权限或外部副作用，至少升级至 REVIEW。

阶段二可在有充分分类能力后进一步区分普通代码中的纯格式变化与行为变化；阶段一除当前任务治理记录外不做该优化。

## 11. Agent、Hooks 与 CI

### 11.1 Agent 文件和 Skill

`AGENTS.md` 与 `CLAUDE.md` 只声明：

- 所有代码任务进入 AI Flow；
- 不得绕过状态、范围和验证门；
- 不得自行降低分流或验证等级；
- 高风险动作需要单独批准；
- 证据和批准必须绑定当前版本；
- 详细 Policy、模板和命令的位置。

`ai-flow` Skill 负责引导 Agent 按命令顺序执行，但不自行计算规则。平台适配内容应引用同一核心流程。

### 11.2 薄层 Hooks

阶段一只建立调用核心 CLI 的薄层检查，用于提前发现范围、状态或命令问题。完整的编辑后范围监控、高风险命令拦截和多平台 Hook 适配属于阶段二。

### 11.3 CI 门禁

GitHub Actions 先解析唯一任务 ID，再调用 `aiflow verify TASK-ID --ci --ci-run-dir <runner-temp-dir> --output <evidence-within-runner-temp>` 和 `aiflow gate TASK-ID --evidence <evidence-within-runner-temp>`，检查：

- 任务记录和事件历史合法；
- 当前分支或 PR 能唯一解析到任务；
- `repository_id` 一致，绝对 checkout 路径不参与比较；
- CI 权威证据绑定 PR 最新 HEAD、被审 `subject_commit` 和相同代码快照；
- `subject_commit..HEAD` 只包含当前任务治理记录；
- 所需验证全部通过；
- 所需规格或代码批准存在且未失效；
- 未批准的外部动作没有被视为允许；
- 本地与 CI 使用相同 Policy 和核心包。

默认情况下，CI 从变更中的 `.ai/tasks/TASK-*` 解析任务；如果无法唯一确定，调用方必须显式传入任务 ID，否则门禁失败。

分支保护的仓库设置无法仅靠代码仓库强制，阶段一应提供配置清单，要求将该工作流设为必需检查并禁止直接推送受保护分支。

## 12. 七章实施设计

### 第 1 章：工程基线与可执行契约

**依赖：** 两份现有架构文档。

**章节任务：**

1. 建立 Python 工程、包、CLI、测试和质量检查骨架；
2. 定义任务、决策单元、分类、批准、事件和证据契约；
3. 建立 Policy、模板和 Schema；
4. 建立 AUTO、ASK、REVIEW、BLOCK 黄金样例；
5. 建立有效与无效契约测试并记录版本规则。

**主要产物：** `pyproject.toml`、`src/aiflow/` 骨架、`.ai/schemas/`、`.ai/policy/`、`.ai/templates/`、`tests/fixtures/`、`examples/scenarios/`。

**退出条件：** 工程可安装；CLI 帮助可运行；所有模板和黄金样例均能通过或按预期拒绝；契约中没有未定义必填字段或未指定枚举。

### 第 2 章：任务记录与状态核心

**依赖：** 第一章契约和目录结构。

**章节任务：**

1. 实现任务编号、目录解析、原子读写和版本兼容检查；
2. 实现 `start`，记录目标、Git 上下文、允许范围和禁止动作；
3. 实现状态转换表、`begin`、`close` 和追加式事件日志；
4. 实现 `status` 的人类与 JSON 输出；
5. 覆盖正常转换、非法转换、重复命令、损坏记录和事件不一致。

**退出条件：** 状态只能经合法命令转换；事件重放与物化状态一致；重复或中断操作不会产生半完成记录；所有状态变化均可追踪。

### 第 3 章：分流与验证等级引擎

**依赖：** 第二章任务存储和状态机。

**章节任务：**

1. 实现决策单元结构和输入校验；
2. 实现有优先级的硬规则执行器；
3. 分别计算 route 与 V0/V1；
4. 实现 `classify` 并持久化规则编号、解释和 Policy 摘要；
5. 使用表驱动测试覆盖黄金样例、规则冲突、缺失配置和边界情况。

**退出条件：** 同一输入和 Policy 产生相同结果；四类黄金样例分类符合预期；每个结论均可解释和重放；Agent 不能自行降低等级。

### 第 4 章：治理交互流程

**依赖：** 第三章分类结果。

**章节任务：**

1. 实现 AUTO 的状态、范围、权限和验证预检；
2. 实现 ASK 选项校验、`answer` 和规格冻结；
3. 实现审核包校验及 `spec`、`code`、`action` 批准；
4. 实现 BLOCK 条件记录和 ESCALATE；
5. 对每条允许与拒绝路径建立集成测试。

**退出条件：** AUTO、ASK、REVIEW 和 BLOCK 均可端到端重放；所有决定和批准包含操作者、时间、版本与理由；代码批准不能替代动作批准。

### 第 5 章：验证与证据闭环

**依赖：** 第四章完整治理状态。

**章节任务：**

1. 根据 V0/V1 和项目配置解析验证计划；
2. 实现带超时、日志和结果归一化的统一执行器；
3. 生成 `evidence.json` 并提供统一复现命令；
4. 实现 commit、规格和 Policy 变化后的失效判断；
5. 测试通过、失败、超时、工具缺失、日志过滤和版本不匹配。

**退出条件：** 所有必需检查通过且证据新鲜时才可放行；失败或缺失检查不能生成通过结论；旧证据不能用于新 commit。

### 第 6 章：Agent 与 CI 集成

**依赖：** 第五章本地闭环。

**章节任务：**

1. 编写精简的 `AGENTS.md` 和 `CLAUDE.md`；
2. 编写只编排核心命令的 `ai-flow` Skill；
3. 建立薄层 Hook 调用点；
4. 建立 GitHub Action 和分支保护配置清单；
5. 验证本地与 CI 对相同任务给出一致门禁结论。

**退出条件：** 缺少任务、证据、批准或正确版本时 CI 必须失败；失败信息指出具体缺失条件；平台适配层没有重复规则。

### 第 7 章：试点验收与阶段一基线

**依赖：** 第六章本地和 CI 门禁。

**章节任务：**

1. 运行 AUTO、ASK、REVIEW 和 BLOCK 黄金场景；
2. 从同一个阶段一基线 commit 建立独立 AUTO、ASK、REVIEW 和 BLOCK worktree/branch，各自在自己的 `subject_commit` 与 attestation HEAD 完成真实试点，避免后续试点使前一任务失效；
3. 将 V0.2 十项验收标准映射到命令、测试和证据；
4. 演练非法状态、越权范围、证据过期和审批缺失；
5. 完成安装、使用、Policy 扩展、故障恢复和阶段一验收报告。

**退出条件：** 十项验收标准均有可复现证据；四个独立试点的权威结果由一个单独的报告任务汇总，报告任务不要求在最终 HEAD 重新 Gate 旧任务；从干净检出可以按文档完成安装和试点；未通过项不得以文字声明代替；阶段二输入问题形成有证据的清单。

## 13. 阶段一总体验收

阶段一完成必须同时满足：

1. 每个代码任务都有唯一且结构合法的任务记录；
2. 每个决策单元都有可解释的分流和独立验证等级；
3. ASK 保存 2—4 个结构完整的选项和用户决定；
4. REVIEW 生成脱离完整对话也可理解的审核包；
5. AUTO 受到状态、文件范围、动作权限和验证门约束；
6. 被审代码、规格或相关 Policy 变化后，旧批准和证据按规则失效；仅治理记录变化不会形成 commit 自引用，且 CI 会在最新 HEAD 重新验证；
7. 单一命令能够重新执行任务要求的全部验证；
8. CI 能阻止缺少任务、证据、批准或版本匹配的变更；
9. 范围扩大、验证异常或新权限需求能够触发升级；
10. AUTO、ASK、REVIEW 各完成一次全流程，BLOCK 完成一次拒绝与恢复验证；
11. 本地与 CI 对相同输入和 Policy 给出一致结论；
12. 从干净检出环境可按照文档完成安装、测试和示例运行。

## 14. 阶段二至四路线图

### 阶段二：审核和强化验证

**进入条件：** 阶段一验收全部通过；真实试点已暴露并记录契约或流程缺口；V2 的实际目标仓库和测试类型已经明确。

**里程碑：**

- `ai-review` 与 `ai-verify` Skill；
- 结构化设计审核和实现审核；
- V2、验收测试、集成测试和定向变异测试；
- 独立 Verifier；
- 更完整的动态升级策略；
- 编辑范围监控和高风险命令拦截 Hooks。

**退出条件：** 一个跨模块 REVIEW 任务完成设计审核、实现、独立验证、实现审核和 CI 放行；V2 证据可以复现；Hook 与核心 Policy 一致。

### 阶段三：高可靠性与模型路由

**进入条件：** 已积累足够内部任务记录；存在需要 V3 的真实用例；模型、费用和返工数据有统一采集口径。

**里程碑：**

- V3、安全检查、故障注入、Dry-run 和回滚演练；
- 模型能力注册表和内部表现记录；
- 基于任务、角色和环境的模型配置选择；
- Claude Code、Codex 和其他模型的角色适配；
- 独立上下文或多模型交叉验证；
- 更严格的分支保护和动作批准。

**退出条件：** 至少一个高风险任务在沙箱中完成 V3 和回滚演练；模型选择能够给出可审计理由；信任度不能覆盖硬风险规则。

### 阶段四：独立编排器

**进入条件：** 多仓库、多平台或多模型任务量已经造成明显的人工协调成本；阶段一至三接口稳定；暂停恢复和集中审批成为真实需求。

**里程碑：**

- 统一模型和平台适配器；
- 并行执行、暂停和恢复；
- 审批界面和预算控制；
- 多机器状态同步；
- 任务队列、可观测性和自动信任度更新。

**退出条件：** 编排器可在故障后恢复任务且不跳过批准或验证；并行任务隔离有效；费用、状态、证据和批准可统一审计。

## 15. 主要风险与控制

| 风险 | 阶段一控制方式 |
|---|---|
| 先写大量模块后才发现接口不一致 | 第一章先冻结契约和黄金样例，每章执行端到端回归 |
| Policy 在 CLI、Skill、Hook 和 CI 中漂移 | 所有适配层调用同一核心包和 Policy |
| 程序无法判断 ASK 选项是否真正不同 | CLI 负责结构约束，Skill 负责语义质量，审核记录保留人工选择 |
| 直接编辑任务文件绕过状态机 | 事件重放必须与物化状态一致，CI 再次校验 |
| 旧证据错误用于新代码或治理提交导致 commit 自引用 | 代码批准与本地证据绑定 `subject_commit`；只允许当前任务治理记录形成 attestation commit；CI 在 PR 最新 HEAD 重新验证并拒绝任何治理目录外变化 |
| 验证命令被拼接或注入 | 使用参数数组、显式工作目录和超时运行子进程 |
| 日志泄露密钥或敏感数据 | 基础过滤、禁止将原始环境变量写入证据、完整日志限制在任务目录 |
| CI 无法唯一识别任务 | 变更解析必须唯一，否则要求显式任务 ID 并默认失败 |
| 过早投入模型路由和复杂公式 | 阶段一不实现，仅保留稳定接口和记录字段 |
| 第一版只在测试夹具中成立 | 第七章必须增加本仓库真实受控任务试点 |

## 16. 设计完成判据

本设计在进入执行计划前必须满足：

- 七章覆盖阶段一的全部目标；
- 各章产物、依赖和退出条件明确；
- 阶段一与阶段二至四的边界明确；
- 不存在未定义的占位任务；
- route、verification、approval 和 evidence 的关系前后一致；
- 每项阶段一验收标准都能映射到可执行命令、测试或证据；
- 用户完成书面审阅并批准进入执行计划。
