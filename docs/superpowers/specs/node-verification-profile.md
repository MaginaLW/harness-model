# Node 目标验证 profile 候选

本文细化[完整引擎跨仓初始化方案](../../operations/sdk-and-engine-plan.md#完整引擎跨仓初始化)中的目标验证合同。它是待审核设计，不是已经可用的 profile、目标 Policy、CI 或接入结果。首个目标已有 Node/npm 项目检查与构建；具体目标、提交、运行环境与授权范围由接入过程核对，不写入本文。目标初始化、资源分发、Policy 采纳和真实应用分别满足各自条件，本文不授予这些动作的权限。

目标是让 AI Flow 的任务分类、独立审核、批准、验证证据和 Gate 对固定的目标候选成立，同时保留目标原有检查。本仓 Python profile 与既有任务、证据和门禁语义保持不变。Node 检查运行项目代码，受信源码和受控环境是前提，不是操作系统沙箱或可信执行器；日志、版本、哈希和独立 actor 标签不认证人员、进程来源或发行方。

## 选择与兼容合同

在目标自己的 `verification-levels.yaml` 中显式声明封闭、版本化的 Node profile。首版固定检查语义和可执行参数，不提供任意命令、任意 shell、动态插件或根据 `package.json` 猜测 profile。未知 profile、缺字段、重复／多余检查、命令与固定定义不符、未支持等级或资源不兼容时拒绝，不尝试旧 profile 或读取其他仓的配置。目标自己的四份 Policy 必须完整、版本一致并经过审阅，不复制源仓身份、历史或常设授权。

现有未声明 profile 的 Python Policy 继续按原版本解析。禁止在读取时向其原始文档注入默认字段后再计算摘要；已有 canonical Policy digest、分类、批准与 evidence 的解释和新鲜度不变。Node profile 的名称、修订及各等级能力作为目标 Policy 的规范内容纳入 Policy 摘要。实际支持的 profile 与证据版本由引擎明确识别；提高能力或调整合同需版本化、重新审阅并使受影响证据失效。

旧 CLI 使用目标仓的 Schema，不能仅靠新增 evidence 版本号声称旧程序一定拒绝。兼容门候选是为新 Node 合同使用目标专属的 Policy 新 major；现有引擎的 `policy.py` 仅接受 major 1/2，新目标 major 必须在旧 loader 阶段拒绝，新引擎才可显式支持。不能修改源仓当前 active Policy 或用旧版本伪装新 profile。验收须以实际旧 wheel 配合升级后的目标 Schema、Node Policy、任务及 evidence 分别调用 classify、verify、approve 和 gate，证明均在产生执行或批准前拒绝；还须检查其他 Policy 消费入口。若某条旧路径不经过此门，先修复兼容设计，不能只凭格式推断安全。目标配置损坏或被恶意更换时不承诺可抵御任意旧程序的绕过；该门不是发布者认证。

## 风险等级与检查集

先以任务事实独立决定要求的 V0、V1 或 V2，再判断选定 profile 是否具备该等级的完整能力。若能力不可用、合同未冻结或工具缺失，保留事实要求的等级并明确阻断；不得把 V1/V2 说成 V0 成功，或仅在报告文字中追加警告后让 Gate 通过。对于原引擎在 V2 Policy 不完整时返回 V1 加阻断的既有行为，新 Node 分支须设计明确且保守的表示，兼容读取端与聚合结果后才能启用。

首个可实现切片的 V0 候选为以下六项，均 required，独立记录结果，按固定顺序执行：

| ID | 固定行为 | 通过只表明 |
|---|---|---|
| `contract` | 原生 task 合同校验 | 当前任务工件符合适用合同。 |
| `scope` | 原生 Git 范围校验 | 固定 base、subject 与允许范围满足原生规则。 |
| `smoke` | 原生 CLI 帮助自检 | CLI 入口可启动，不证明目标检查通过。 |
| `node_check` | 经核定的 Node/npm CLI 执行 `npm run check` | 目标固定提交中该脚本及其调用链退出成功；须明确覆盖的类型、测试和文档检查。 |
| `node_build` | 同一受核工具链执行 `npm run build` | 固定候选构建成功；构建输出只允许写隔离副本或明确的受控位置。 |
| `diff_whitespace` | Git 对固定 `base_commit..subject_commit` 执行 `diff --check` | 指定提交差异的空白检查通过；不能用干净工作区的空 diff 冒充。 |

不把 Node 的退出码映射为 Ruff、mypy、Python 测试或覆盖率成功。所有目标脚本、配置、锁文件和实际检查范围须在冻结候选中核验。V0 只是低风险任务的一个阶段性 profile，不意味着普通代码改动可以避开 V1，也不代表完整跨仓引擎交付。

V1 必须包含 V0 的完整等价前缀并有目标真实测试和覆盖率合同。目标若原本没有覆盖率工具或阈值，应如实记缺失，不能将本仓 85%／90% 写成目标既有事实。须先选定受审的目标源码清单、总覆盖指标与阈值、变更可执行行口径和阈值、base/subject、报告格式与解析器；审查维持或加强目标现有规则的影响，再实现和验证。固定 Vitest 与匹配版本的覆盖提供者和锁文件；把未导入的 tracked 源文件计入总体，校验原始源路径与 sourcemap。对被修改或新增的可执行行，缺报告或映射未知不能当成没有可执行行；重命名、删除、仅文档差异、空集合、二进制和不支持语言分别有明确规则。

若检查范围候选只包括 TypeScript 源，JavaScript、PowerShell、C# 等生产脚本及子进程执行不自动受覆盖。任务变更触及未纳入的可执行文件时，必须提供经审核的相应检查与覆盖方式，或明确 unverified 并阻断；不通过缩小路径、只统计已触达文件或删项伪造覆盖。测试／构建退出零、覆盖率通过都不证明真实消息服务、模型或生产系统已验收。

V2 在完整 V1 之外仍须具备 acceptance、integration、独立 Verifier、定向变异及独立实现审核，并满足原有审批、finalize 和 Gate 时序。现有五项变异针对 AI Flow 自身 Python 治理保障，并绑定源路径；外仓不含这些文件，简单换成目标业务路径不是等价证明。正式启用前另行设计经审阅的固定引擎来源、构建及变异清单，绑定其字节／版本与运行引擎，并将引擎、目标 repository/base/subject、Policy/profile、独立职责、单次动作和不可变结果共同纳入可重核证据。缺失、身份不明、未执行、survived、超时或无法验证的变异均阻断；旧历史结果不自动迁移给新引擎或新目标。

## 执行与绑定

验证先固定目标完整 Git 根、repository ID、base、subject、脚本与锁文件 Git 对象，并核实提交祖先、范围及工作区状态。与目标活动工作区分离的可丢弃 Git 检出必须可核对相同 commit/tree；不能把重建后不同 commit 的工作树冒充原候选。linked worktree、嵌套仓、大小写、符号链接和 Windows junction 按根目录合同拒绝越界；不带真实 `.env`、运行库、凭据或用户会话。目标已有修改或其他 writer 时保留现场，实际应用前再次确认写入交接。

通过受核定的 Node 可执行文件与同一安装中的 npm CLI 以固定 argv 运行，记录实际 Node/npm 版本、来源可证明范围及必要摘要。Windows 不把 `.cmd` 经隐式 shell 调用当作安全保证；工具解析及参数使用专门验证的直接入口。工作目录、环境、输出目录和超时封闭；隔离执行根若不在原仓内，须显式设计其与目标固定树的绑定，不能为实现方便放宽现有 runner 的任意 cwd 限制。依赖安装按锁文件及目标约束处理，安装脚本、网络或项目脚本可能产生外部副作用：无相应授权或无法验证其边界时停止，不将有限环境称为网络隔离。

每次结果应逐项绑定目标任务、repository ID、base、subject、规格、Policy 摘要、分类输入、profile 修订／语义摘要、实际执行脚本和锁文件的 Git 对象、核实过的工具链版本及环境边界。检查记录包含固定检查 ID、所运行命令身份、required、退出状态、超时、日志引用和必要输出工件的摘要；缺项、重复、顺序或绑定不符、结果未知、超时和输出解析失败均不可产生 passed。对部分 `--check` 维持 provisional，不能进入 Gate；local 与 CI 分别对同一候选重核输入与 profile，不能将 local 回执伪装成 CI。

Node evidence 若采用新的版本，须在合同、装载、审核上下文、批准、freshness 与 Gate 的每个消费者显式分支，并由目标 Policy major／引擎兼容门共同约束；不能只在 Schema 增加枚举后让旧代码落入 legacy 分支。Gate 和批准须根据当前 profile 独立核对精确的 required 检查集合、结果与摘要，并核对完整 evidence hash；不能仅相信 `conclusion=passed`。V2 在此基础上维持独立 verifier context、review/finalize、变异和完整快照语义。对结果与身份不确定保留 unknown，不声称哈希或 actor 标签构成身份认证。

## 验收与交付依赖

1. 先冻结目标场景、完整检查与安全边界；核实包资源、目标身份、Policy 种子和兼容矩阵。审阅新 Policy major、profile、evidence 及 V1/V2 缺失时的分类／阻断合同。Python 老版本与历史输入作为不可改写回归。
2. 共享合同确定后，Policy/Schema 与分类、验证计划及 runner 可按不重叠文件并行实现；资源清单依赖所有 Schema 的最终字节，须在集成时同步，不能并行覆盖。然后串行整合 evidence、freshness、审核、批准和 Gate，执行独立设计与实现审查。
3. 在可丢弃 Git 仓验证 Node V0 六项成功和逐项失败：错误／缺失脚本或工具、非零退出、超时、未知 profile、检查缺失／重复／额外、错误工作目录、脚本／锁／提交／工具链变化、路径越界、partial、篡改 evidence、缺失审核或批准均拒绝；真实 old wheel 配新目标资源/Policy 的兼容性反例不可跳过。
4. V1 启用前验证未导入文件、未覆盖变更、源映射缺失、非支持语言、重命名、删除、空 diff 和两份输出的摘要绑定。V2 独立完成引擎变异、单次批准、独立角色、前后快照、失败和恢复反例。未完成的等级不得通过，也不能把 V0 合成结果当作 V1/V2 证据。
5. 保持本仓完整测试、各源码域 85% 总覆盖率、90% 变更覆盖率、whitespace、Ruff、format、mypy、required CI 与分支保护；目标检查另按最终合同和目标规则执行。只在隔离端到端与独立审核完成后，对真实目标生成非覆盖计划、核验当前写入权并按适用授权实施；外部设置、部署和真实服务另行处理。
