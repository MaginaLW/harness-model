## 3. 基础设施主线：先完成一个仓库的全部 CI

| 顺序 | 对应计划 | 工作与退出条件 |
|---|---|---|
| 先冻结现状 | I0 | 复用本轮真实交付，读回分支、main、runner 和原 job 清单；形成简短范围决定，不重复最小试点 |
| 下一执行阶段 | I1 必要准备 + I2 同仓扩展 | 准备真实 Linux 环境；Linux 冒烟后迁移剩余 job；同一最终提交上 Windows/Linux 原有必要 job 全部真实通过，形成完整 workflow 的 PILOT_PASS |
| 随后正式采用 | 01 的 ADOPTED 定义 + I1/I2 | 补必要恢复验证，审查最终差异，经具体 PR/main 授权进入实际生效分支并验证；此后才标 ADOPTED |
| 再整理复用能力 | I1 其余部分 | 按实际经验收敛盘点、健康、安装状态判断、更新、日志和回退；正确安装不重复注册，原工具与质量门保留 |
| 有需求再扩仓 | I2 后续 | 每次一个明确选择的可信目标，独立核对平台、权限、注册范围、资源与完整 CI；没有需求可以暂不接入 |

### 下一阶段的具体范围

1. **先只读检查。** 核对当前目标和全部 workflow、GitHub 权限与可触发人员，检查
   Windows 虚拟化支持、现有 Linux/虚拟机资产、CPU/内存/磁盘余量、账号与共享边界。
   不因为本机有 WSL 命令就宣布 Linux runner 已就绪，不预设硬件足够。
2. **形成可审阅候选。** 优先评估同一物理机上的隔离 Ubuntu 虚拟机，让 runner
   实际运行在 Linux 内。明确发行版、vCPU/内存/磁盘、运行身份、工具和网络需求；
   不默认共享个人 profile、凭据或业务工作区，不把 Windows labels 当 Linux 平台。
3. **先约束整机负载。** Windows 与 Linux 实例共用物理资源。接任务前明确可验证的
   串行策略或经核定的资源边界；单实例串行和仓库 concurrency 不证明整机受控。
   只采用当前范围能验证的简单配置，不提前建设 I5 调度器。
4. **集中核对新增授权。** 候选和回退材料准备好后，再核对虚拟机/系统功能、账号、
   共享与网络配置、Linux runner 注册及服务、POSIX 路由、push 和真实验证的确切范围。
   新阶段的失败处理与修复次数必须明确，不能重新使用已消费的旧诊断 guard。
5. **获准后先 Linux 冒烟，再迁移真实 job。** 原有平台语义、依赖信任、权限、
   触发、job/required-check 名称、测试、阈值和超时保持；必要差异逐项说明。
   不能以删除 POSIX 检查、直接套 Windows 或自动退回收费托管路径完成验收。
6. **以最终版本验收。** 核对 Windows/Linux 各必要 job 的真实 checkout SHA、
   runner 身份、步骤、最终 conclusion 和日志。旧 Windows PASS 是基线，
   新 workflow 的完整成功仍须实际验证。只有两个平台均成功才结束这一阶段。

最低安全和运维条件必须在 Linux 接任务前具备，不能推迟到“运维标准化”再补。
正式采用前验证所依赖的启动/停止与恢复路径；服务重启、Linux guest 重启和 Windows
整机重启分开记录。需要重启日常电脑时先安排明确窗口，不擅自重启或改变电源策略。

这里的“全部本机化”指该目标已盘点的 CI 计算。GitHub 仍负责触发、排队、Checks 和日志；
产物/缓存、外部 API 及软件许可分别处理。电脑离线时不能保证 CI 可用。
公开仓库继续保留标准托管 CI，不开放不可信 PR 在日常主机上运行。
macOS 检查必须保留真实 macOS 平台；不承诺 Windows/Linux 覆盖任意仓库的所有任务。

### 正式采用与回退

完整试点通过后，先准备并独立审查具体 PR 差异和验证材料，再集中核对 PR/main 的
授权；不从本页或已有 Windows A–E 推导合并权限。进入 main 后仍以实际生效版本的
运行结果核定 ADOPTED。任何 required check 失败都不能通过降门禁完成采用。

每阶段保留精确变更和恢复路径。Linux 新接入失败时按批准范围停止该实例接任务、
保留诊断并定向撤回本阶段变更，保留已验证 Windows 实例；注册删除、服务卸载和
清理目录分别核对授权。恢复 hosted 可能仍受原有账户条件限制，不承诺回退后立即运行。
