# 接入现有 AI 工作流

建议先用 **ZCode + 一个已有项目 + 低风险真实工作** 试点，再逐项目推广。
先复用低干预工作约定和目标项目自己的质量检查，不默认接入完整 AI Flow 审批链。
这是一条轻量使用路径，不代表 AI Flow 引擎已具备跨仓库即装即用能力，
也不改变 harness-model 本身的治理模式、升级清单或质量门禁。

## 选择接入深度

| 层次 | 当前用途与边界 |
|---|---|
| 工作约定 | 推荐起点。合并少量通用规则到目标项目已有指令入口，保留本项目原有安全与治理规则；不安装依赖、Hook 或后台服务。 |
| 项目验证 | 沿用目标仓库已定义的测试、静态检查与 required CI。没有检查时如实标缺失，不靠复制本仓 Python 命令制造通过结果。 |
| 完整 AI Flow | 仅在确实需要确定性任务分流、版本绑定审批与证据 Gate 时评估。当前外仓初始化和运行定位仍有缺口，见下节，不是普通试点的前置条件。 |

推广的是“同一原则 + 项目适配”，不是向所有工具、项目复制同一套配置。
对已有强制流程的仓库，轻量规则不能解除其任务或审核义务；冲突先按该仓规则处理。

## 先做只读盘点

在可信的 harness-model 检出中运行，使用 Python 3.11+ 和 Git，不要求在目标项目安装 aiflow：

```powershell
# 从 harness-model 根目录运行；把占位符换成目标项目或其中一个子目录。
.\.venv\Scripts\python.exe -I -B tools/analysis/repository_readiness.py --repo "<TARGET_REPO>" --format text
```

```sh
.venv/bin/python -I -B tools/analysis/repository_readiness.py --repo "<TARGET_REPO>" --format json
```

工具仅盘点本地 Git 状态和有限的常见入口，不输出配置正文、不运行目标项目代码、
Hook 或测试，不安装或写入文件，不调用模型或网络。它不是安全沙箱：目标 Git 配置
仍可能影响 Git 自身的读取行为，应使用可信 Git 与获准检查的本地仓库。
输出包含本地路径，只供本地判断；不要将原始输出、身份、路径或配置内容直接提交。

退出码 `0` 只表示盘点完成，不是准入、质量通过或动作授权；`2` 表示盘点失败。
存在指令、CI 目录或 `.ai` 资产也不证明它们有效、已被 Agent 加载或远端保护已启用。
工具不扫描所有嵌套规则和自定义 CI，不判断付费权限，也不自动选择验证命令。
请传入不含 `..` 的直接路径；目录链接或重解析点会被拒绝，固定入口中的链接只标记而不跟随。
Git 盘点隔离用户级/系统级配置，不包含子模块内部脏状态，因此不是日常 Git 状态的完整替代。
若本地、include 或 worktree 配置包含 clean/process filter，工具只查键名，跳过状态计算，
将脏状态标为 `unknown`，避免只读检查意外运行过滤器；它不会把未知当作干净。

随后由 Agent 在已授权的目标范围内阅读相关规则与 CI，确认三个事实：
实际工作区根目录、可执行的原有质量命令、哪些动作确实需要人类决定。
已有未提交修改保留；缺少 Git 提交、测试或 CI 时，报告限制，不自动初始化或覆盖。

## ZCode 首批试点

这里指智谱 / Z.ai 的 ZCode Agent，不是同名开源 CLI。2026-09-08 核对的
[官方文档](https://zcode.z.ai/en/docs/agents)说明：它在新任务启动时读取用户级及当前工作区
`AGENTS.md`，不逐层合并父子目录规则，也不展开 import/include；`CLAUDE.md` 不是持续读取入口。
因此，应在实际项目根目录打开工作区，把关键规则直接放在入口，局部规则由 Agent 按范围读取。

1. 选一个已有测试、可恢复的小修复或文档工作项。未选外部仓库时，可先在本仓做下述只读
   冒烟检查；这仅确认指令接入，不是效率效果验收，也不为试点制造无意义的业务改动。
2. 如需修改目标指令，先对照[通用规则片段](../../examples/adoption/project-rules.md)，
   只合并缺失且不冲突的条款，展示实际 diff；已有等价约定不重复添加。
   片段文件本身不被自动加载，不能直接用它覆盖整个 `AGENTS.md`。
3. 在新 ZCode 任务中使用[试点提示词](../../examples/adoption/zcode-pilot-prompt.md)。
   先只读核对根目录、规则与命令，再执行用户已经指定的普通任务；没有具体任务就停在只读结果。
4. 首轮保留现有模型、权限、账户与费用设置，不启用全局 Hook、记忆采集、自动任务或外部执行器。
   不复制 harness-model 的 `.codex/config.toml`，也不假设两个产品支持相同的子智能体模型组合。
5. Agent 连续完成已授权实现、必要验证与可恢复修复，并按目标项目规则提交。
   业务选择、规定的人审和真实外部动作仍保留各自边界；本地测试通过不代替发布授权。

ZCode 的执行模式还会影响确认次数：官方文档将“修改前询问”列为默认，
“自动编辑”仍保留命令确认。低风险试点可以考虑后者，但应由使用者选择，
不能为压低计数自动改为 Full access 或关闭保护。
指令文本不构成命令拦截器；减少流程重复询问不等于消除产品本身的权限弹窗。

## 真实任务的执行与收尾

以下方法复用目标项目的现有命令、进度入口和证据位置，不新增安装步骤、固定报表或审批。
首批外仓代码任务暴露的具体问题与证据见 [ZCode 接入反馈](zcode-adoption-feedback.md)。

1. **核对命令和交付链。** 执行前从脚本、文档和 CI 确认精确命令、用途、写入范围、
   隔离环境及前提，不能凭 `sync` 等命令名认定只读。涉及产物格式、Schema 版本或接口的
   变更，定位生产端、注册/声明的 Schema、测试与 CI 消费端，并核对版本和字段是否一致。
   对当前候选版本分别报告局部检查、全量检查、远端 CI 与发布状态；每项附其实际被测版本。
   旧提交的 CI、尚未执行的后续步骤和本地通过都不能补成当前候选的整链通过。
变更生效所经的每一层配置都要定位并逐层核对：区分自动同步清单与静态手工清单
（后者不随服务 reload 自动更新），链路 canary 以最终可观测行为为准，不以上游
组件的局部通过为准（实例来源：r3s-VPS 域名策略分散在 DNS 按域转发、rebind
白名单、DNS policy 与路由规则四层，只改后两层时 DNS 抽测当场抓到污染残留）。
2. **留下可复核的验证摘要。** 按[效果观察方法](effect-observations.md#下一批真实工作如何观察)
   保留被测 commit/tree、工作区状态、命令、结果及可读取的脱敏摘要引用，哈希用于校验，
   不替代摘要正文。失败和重跑保持关联；历史材料已缺失时如实记录，不自动重跑来补写历史。
   验证输出自身含非确定部分（生成时间戳头、计数器、一次性标识）时，先剔除这些部分再
   逐字节比对或哈希，并把剔除规则写进证据记录，避免把输出格式的时间漂移误判成内容漂移。
为审查或回执生成脱敏摘录时，用节锚点自动切取并内置凭据模式断言，不用手工行号
切片：r3s-VPS 一批曾按行号切片把凭据节带进审查材料，写后凭据断言才抓获并重制。
记录"已修复/已核对"类结论时，绑定当次修复提交与验证结果；反馈已记录或核对项已
固化不等于消费端已修复——ai-agent-dotfiles 的 SchemaVersion 漂移在反馈记录并
固化为核对项后仍致 CI 连续失败，直到修复提交 `895c54f` 才闭环（实例来源：
ai-agent-dotfiles 收尾记录曾误写"曾发现并修复"）。
反向结论同样要绑定：写"仍失败/仍是红的/未完成"时，绑定产出该结论的那次运行
（被测 tree/commit、命令、结果），并把它当作关于那次运行的陈述，而不是对当前
工作树的判断；跨会话转述或据此开工前先重跑或重新核对，否则会重做已经完成的
工作（实例来源：ai-agent-dotfiles 连续两个会话在 STATUS 记录 canonical-hard-kill
"仍是红的、12 个自密封钉陈旧"，而工作树在更早一次重新密封后已经自洽——
按记录开工等于重做一次已完成的重新密封）。
门禁结论只能读门禁自身的退出状态：把门禁输出接进管道（`| tail`、`| Select-Object`、
`| Tee-Object`）再按管道或后续命令的状态决定动作，会把管道末端的成功当成门禁通过。
实例来源：ai-agent-dotfiles 2026-09-16 —— 提交前把 secret scan 接到 `tail` 后串联 `&&`，
扫描实际以 1 退出（新文档里一个 `task-overlay-…` 字符串撞上 key 正则）而提交照常产生；
修法是先把门禁输出写入文件、再单独读取门禁自身的退出码或断言其输出文本，且修的是被
误报的内容本身，不是扫描器。
远端流水线页面的失败展示是压缩摘要，不构成根因证据：定位红灯必须取该次运行的原始执行
记录（job 日志、报告或等效产物），页面标注与结论徽标只用来确定失败发生在哪一步；取了
日志再按记录结构判读，并把结论绑定到该次运行。实例来源：ai-agent-dotfiles 2026-09-17 ——
该仓 57 次非成功运行中 55 次的页面标注只有一行 "Process completed with exit code 1."，
真正的根因（产物 Schema 漂移、套件预算耗尽、被杀进程夹具的共享冲突、runner 失联）只在
job 日志里；日志端点在重定向到对象存储后要求剥离授权头，保留凭据跟随重定向的客户端会
拿到 401，看起来像权限问题而不是取数方式问题。
记录被门禁或扫描器拦下的实例时，描述命中形态，不要复现被拦的字面量：门禁按模式扫描，
记录里的示例同样会被扫到，于是记录本身被拦。实例来源：ai-agent-dotfiles 2026-09-17 ——
新增的 CI 失败规则文件在"secret 门禁误报"一节照抄了被拦的赋值形态，扫描器随即以退出码 1
拦下文档自身那一行；改为拆开描述后通过，修的是记录写法而不是扫描器。
3. **审阅验证范围变化。** 对照本次与基线的测试发现范围，说明新增、停用、改名或移入
   非执行目录的检查，以及替代验证或恢复计划。套件数和“发现的全部通过”不能证明原有
   检查仍被执行；必需检查不得通过改名、搬目录或排除规则静默退出执行。
同一教训第二次出现时，把它转成可执行检查（lint、断言、模板或脚手架），
   不要只再写一条记录：记录型教训不会在下次写代码时自动生效，转成检查才能在提交前拦住
   复发。已知但暂时不能修的实例用**显式、可搜索的豁免清单**（文件 + 精确行号 + 原因 +
   计划）保留可见，其余新出现一律致命，避免"整类模式被静默放过"（实例来源：
   ai-agent-dotfiles 的 PowerShell `if (Cmdlet ... -and ...)` 解析坑在记录后一个窗口内复犯，
   现改为基于 AST 的解析门禁规则——命令参数里出现 `and`/`or` 即失败——并对一个自密封
   测试文件中的既有实例保留带行号的豁免项）。
后续阶段里"只做核对"的步骤同样要落成可执行断言，而不是一次性人工复核：核对上一阶段
   已冻结的 Schema、字段集或判别分支时，把关键集合（必填字段、分支枚举、引用方向）钉进
   测试或契约注册表，冻结就不会被后续改动静默改宽或改窄。有真实生产端时，断言应由生产端
   产物派生（在隔离环境里实际生成再检查）；静态 fixture 只能证明形状可表达，不能证明发射端
   仍一致，且只有 schema、没有注册契约与 fixture 的产物视为未验证（实例来源：
   ai-agent-dotfiles Phase 3 Task 1 把 Phase 2 已交付的锁 schema 冻结、共享状态判别分支与
   authority plan 分支三条核对步骤转成生产端派生的图断言与分支钉值，并为此前未注册的
   env lock 补上契约与 5 条图反例）。
   验收断言不得绑定工具自身的本地化文案（例如 PowerShell 的参数绑定错误消息），
   改用稳定的错误 ID 或项目自有 token 匹配；否则同一提交在不同系统语言的主机上会得出
   不同的门禁结论，而且本地门禁可能在 CI 长期绿灯的情况下失效（实例来源：
   ai-agent-dotfiles 的 unified run 在 zh-CN 主机上因 7 处 `missing mandatory parameters`/
   `because it is null` 文案断言中止，CI 为 en-US 故此前一直未暴露，改为匹配
   `MissingMandatoryParameter`/`ParameterArgumentValidationErrorNullNotAllowed` 后本地恢复通过）。
组合层里测试无法触达的分支等同于未验证：只在罕见状态组合下才走到的分支（例如"存在有效
   权威状态、定义未漂移且锁字节匹配"的那条路径），评审才发现必然崩溃、而套件长期全绿，
   说明分支本身没有被任何测试驱动。把这类分支抽成共享函数，让测试能直接构造其输入并钉住
   输出；同一任务内同一类错误第二次出现时照旧转成可执行检查——例如"调用仓库函数时使用了
   对方不存在的参数名"可以基于 AST 建立签名表并在生产脚本范围内判失败（跳过重名定义与
   `dynamicparam`，接受别名参数与公共参数；测试文件因存在同名本地 helper 与外部工具 shim
   不参与建表），并以一次 RED 对照证明门禁真的会失败（实例来源：ai-agent-dotfiles Phase 3
   Task 2 —— 该分支是健康权威状态的唯一 status 出口却无测试覆盖，评审后抽成共享函数并补测；
   同一任务内 `-Path`/`-StagingPath` 参数名错误出现两次后加入参数名门禁，806 个签名零违规）。
   清单式规则（"改了 X 就必须同步重钉 Y"）以复现为准：动手前先独立计算并与钉值比对，复现可以
   合法地得出"无需改动"——这时照抄历史数字、或凭规则盲目重写钉值，都是把未经核对的清单当成
   结论（实例来源：ai-agent-dotfiles 2026-09-15 两次修改 `scripts/**` 后复现
   canonical-production-seams 的两个 all-scripts 基线，均为字节相同，据此判定不需重钉）；
   门禁规则本身也要按其断言的目标复核，例如同一门禁用大小写敏感比较 `and`/`or`，就会放过
   `-AND` 这类等价写法（该缺口由独立评审发现，补上后以 RED/GREEN 对照证明生效）。
   并行写入同一仓库时，共享的冻结基线要在整合后的树上复现一次，而不是采用任何单路的结果：
   各路在自己的一次性检出里各自复现都可能是对的，但最终产物是组合体。实例来源：
   ai-agent-dotfiles 2026-09-16 的五路并行——一路改 `scripts/**` 使反射敏感计数与摘要移动，
   另一路只做缩进整理却因该基线按 extent 文本哈希而移动了另一个摘要（语义中性、空白敏感）；
   两路各自的重钉都自洽，只有组合树的值才是最终钉值，由整合方重算并逐行核对增量与改动一一
   对应后才落钉。同理，整合方要复现"无需重钉"的结论，而不是照抄任一路的判断。

4. **区分实际耗时与预算。** 收尾引用已有的实测耗时、配置超时上限和重跑原因，分别记录
   真实超时、环境问题、测试增长或实现修复；提高上限不表示执行更慢，也不证明优化有效。
   定位单项超时前先确认它的**生效**上限：没有显式条目的项会继承默认值，个别用例因此悄悄
   挂在最短档上；把本机实测与生效上限对照，才能分开"预算不足"与"实现变慢"（实例来源：
   ai-agent-dotfiles 2026-09-17 —— 一个本机 80 s 的套件挂在 120 s 默认档上，三次 CI 记录里
   只有超时标记、没有任何用例记录；给出显式预算后与运行器自身的合同口径一并复核）。
   模型身份、费用、人时或失败原因无可靠来源时保留 `unknown`，不根据等待时长推算。
   把长时间验证包在外部超时里时，上限要由运行器自身声明的需求推导，不能用记忆里的历史耗时：
   被截断的运行不构成结论，它只说明已跑完的部分没有失败，其余检查没有结果，既不能记成通过，
   也不能用"零失败"代替未跑完的清单（实例来源：ai-agent-dotfiles 2026-09-15 的统一跑——按记忆
   中的 87-105 分钟设了 150 分钟上限，实际超过上限被截断，约 30 个套件零失败但摘要未写出，
   既不是通过也不是失败，只能陈述"该次运行已跑部分无失败"并重跑）。
5. **用紧凑摘要接手。** 在项目原有权威进度入口维护当前摘要或最新条目的指针，先读当前
   工作和未验证项，再按指针读取相关历史。历史记录保持原处；若入口要求追加式，追加新
   条目，不改写旧结论，也不另建第二份权威进度表。追加式入口还要给被推翻的旧句加标记：只追加
   新条目而不标注，同一文件会同时留下两种现在时态的说法，读者无法判断哪一句有效，而这正是
   "按记录开工"类事故的入口（实例来源：ai-agent-dotfiles 2026-09-15 的当前任务记录在文件头
   同时写着 Phase 3 "16/47" 与 "7/47"、并指示"从 Task 1 继续"，而同一文件文末是 47/47；
   STATUS.md 的 wrap-up 标题与它自身的正文更正并存。修法是给历史节加 Superseded 横幅或把句子
   改成过去时，而不是再追加一条更正）。
6. **独立评审分两段，并给评审本身设边界。** 引入第二模型或独立 worker 评审时，方案评审
   与变更评审分开：实现前评方案（分类规则、要复用的现有接口、禁止复用的路径），实现后
   只评未提交的 diff，并在提示里限定文件清单、严重度分级、最多条数和"无缺陷必须显式说明"。
   要求每条结论落到 `file:line` 与可复现场景，评审方只报实读到的内容，不重述 diff、不凑数。
   评审范围不设边界会撞上评审方自身的单次预算而被取消，收敛范围后同一份 diff 反而能给出
   可执行结论（实例来源：ai-agent-dotfiles Task 6 Step 3 的两轮只读评审——设计评审在动手前
   修正了状态恢复方案与状态归类规则；实现后的对抗式 diff 评审在同一改动里又找到两个真实
   缺陷（失效的交叉校验、已 staged 未替换的状态窗口）和一个缺失的失败注入用例；两次不限
   范围的评审先被取消，收敛到 4 个文件、≤15 条、必须给出严重度后，第三轮在 15 个回合内
   完成）。评审发现按缺陷、缺口、建议分级后逐条落地或明确记为边界；独立评审不改变权限、
   并发边界与门禁，修复仍由目标仓原有检查重新验证，评审通过本身不算验证。
设计阶段的评审同样要设边界：要求"先读完整方案与相关代码再回答"的提示，规模一大就会
   超出评审方单次预算并被中途取消；改为给定文件清单加具体决策点（分类规则、要复用的接口、
   禁止复用的路径），评审方仍需读实现细节才能回答时再逐步给下一个文件。取消或失败的评审
   按"没有评审"处理，不能记作已评审，也不要在同一提示上反复重试——先收敛范围再发起
   （实例来源：ai-agent-dotfiles Task 6 Step 4-5 的设计评审连续两次以 error_during_execution
   中止，而此前限定"4 个文件、≤15 条"的短评审一次完成）。
   并行安排多路评审时，权限模式要与任务匹配：只读/计划模式通常拦截需要执行的命令，要跑
   `git show`、AST 解析或哈希重算的评审会以 error_during_execution 中止，按"没有评审"处理；
   给每路一份一次性检出（如 `git worktree`）加完全权限，既不互相等待也不触碰主工作树，同一批
   提示词即可跑完（实例来源：ai-agent-dotfiles 2026-09-15 的四路并行复核——先以只读模式发起，
   三路被取消；改为一次性 worktree 加完全权限后各自在 9-11 个回合内给出可复现结论）。
   排并行计划前，把工具说明里的并发说法与实现对照一次：说明与实现不一致时以实现为准，
   并把说明改对，否则下一次会话仍会按旧文本排计划。实例来源：ai-agent-dotfiles 2026-09-16 ——
   其全局 Grok 调用说明称"只读分析类可与任何调用并行"，而封装脚本按工作目录加命名互斥、
   无论权限模式都拒绝同一目录的第二个进程，只读（plan）模式还会取消需要执行命令的评审；
   本次按实际行为改说明（每路各自工作目录/一次性检出），并把封装脚本的实际参数上限一并记入。

当前摘要可以沿用下面的结构，填入已有事实即可，不要求每个任务另建文件：

```text
当前候选：<commit/tree>；工作区：<clean/dirty/unknown，相关未提交范围>
正在做 / 下一步：<当前工作与尚未完成项>
验证：<局部、全量、CI 各自的结果和被测版本；未执行项明确列出>
运行前提与命令：<准确命令；用途；写入范围；隔离环境和必要前提>
证据 / 历史：<可读取脱敏摘要、失败与重跑记录、原有历史条目的指针>
```

## 将反馈应用回试点

所有者明确登记的试点统一采用[任务收尾反馈闭环](feedback-loop.md)：完成真实任务、
汇总新反馈、在本仓改进通用方法、验证并提交，再按版本将适用条款合并回目标项目。
下一项自然发生的任务检验这些改动，不能为凑样本自行开始业务工作或回放历史运行。

先由目标 Agent 在当前任务结束后执行[首次接入提示词](../../examples/adoption/zcode-feedback-loop-prompt.md)，
将入口持久化到项目既有指令中；登记本身不代表已经接入。本轮只准备方法与提示词，不抢写
正在执行任务的目标仓。当前范围为 `ai-agent-dotfiles` 和 `r3s-VPS`；新增项目须由所有者
明确登记，并先完成该项目入口、规则和验证适配，不能扫描全部本地仓库自动推广。

这是 Agent 在任务边界执行的流程，不是自动复制全部规则或后台同步服务。同一反馈不重复
修订；没有新反馈且适用规则无变化时不改文件。有权限、并发写入、证据或原有门禁问题时，
记录待处理位置与原因，不绕过它们。每个项目独立记录已应用版本、反馈窗口和验证，不将
一个项目的通过或缺陷推定为另一个项目的结论。

## 如何判断值得推广

在接下来自然发生的同类任务中观察，不新建逐次填报或审批程序。
每个完成窗口由 Agent 根据已有事实汇总一次，复用
[效果观察口径](effect-observations.md#下一批真实工作如何观察)：

- 分开记录业务/风险决定、已有有效决定的重复请求、产品权限弹窗；看不到弹窗全量时写 `unknown`。
- 保留任务类型、提交范围、原有验证结果、明确返工和交付后缺陷观察状态。
  没有人类自报用时就写 `unknown`，不拿聊天等待时间或批准条数换算人时。
- 若有可比旧任务，按相同类型与观察窗口比较原始值、样本数及缺失项。
  没有对照或缺陷观察尚未结束时，只报告可用性，不宣布效率或可靠度改善。

当真实任务能在原有质量门下完成、重复流程请求没有出现且规则接入没有冲突时，
可以扩大到下一个低风险项目；这只是渐进推广依据，不是统计上的效果证明。
若必需检查被跳过、边界动作越权、规则冲突或重复请求增加，暂停该项目的扩展，
先定位原因。只撤回这次新增的规则条款，保留用户改动、原有保护与失败证据；
不要删全局配置、历史账本或通过关闭保护恢复“流畅”。

## 再推广到 Codex 和其他工具

Codex 的[官方 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
规定了从项目根到当前目录的指令发现，并在同目录优先使用 `AGENTS.override.md`。
这与 ZCode 的工作区入口不同；修改后需在新运行中核对实际加载的规则。
这里使用官方说明校准入口，不修改全局 Codex 设置或现有模型路由。

对其他 Agent，只适配其经核实的指令入口，不假设它会自动读取 `AGENTS.md`、
`CLAUDE.md` 或本仓的 Skill。纯聊天、文档类 AI 没有代码工作区和 CI 时，复用目标、
边界、验证证据与必要决定的原则即可，不要求伪造 Git task。
每次只推广一个工具与项目组合，复用已完成的项目检查，不反复让人确认相同事实。

## 完整引擎的跨仓库边界

当前 `0.2.0` 的[Quickstart](quickstart.md)针对 harness-model 的完整克隆。
仅安装 wheel 或执行 `pip install` 并不能把另一仓库变成 AI Flow 项目：

- 包只分发 `src/aiflow`，运行时仍需仓库自己的 `.ai/repository-id`、Policy、Schema、
  模板与任务存储。不得复制本仓身份、历史 task、批准、证据或维护模式标记。
- 多个 CLI 入口及默认 Schema 查找依赖当前目录；目前使用完整克隆时在仓库根运行，
  不把只读盘点工具的子目录支持解释为 AI Flow CLI 已支持任意子目录。
- 新 task 的分类前仍需由 Agent 按实际情况填写显式风险事实，见
  [Quickstart 的草稿步骤](quickstart.md)；缺字段不是向人类求批的理由。
- 本仓 CI 命令、路径、85% / 90% 阈值及维护模式是本仓约束，不是外仓通用安装模板。
  外仓必须映射自己的质量检查与治理模式，不能通过复制 bootstrap 标记跳过原有 Gate。

因此，全引擎外仓产品化仍需独立设计和验证：安全且不覆盖已有配置的初始化与资源分发、
统一仓库定位、显式草稿事实录入，以及目标 CI 适配。源于
[`pyproject.toml`](../../pyproject.toml)、[CLI](../../src/aiflow/cli.py)、
[仓库身份](../../src/aiflow/git_context.py)、[Schema 加载](../../src/aiflow/contracts.py)
和[任务存储](../../src/aiflow/storage.py)的当前实现核查，不是已存在的安装命令。

真实项目需要这一层时再按本仓 AI Flow 创建治理变更并验证干净外仓端到端流程；
它不阻塞轻量试点，也不授权自动恢复强制 task、阶段三/四、模型路由或可信外部执行器。
现有 [Hook wrapper](hooks.md)仍不执行或授权 push/merge，不能拿来伪装通用安全控制面。
