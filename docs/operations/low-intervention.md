# 低干预工作方式

目标是让 Agent 完成已授权范围内可验证、可恢复的工作，把人类注意力用在真正缺少的方向
决定和授权上。本页解释现有维护模式与 CLI 的使用方式；分流、批准、验证强度与 Gate
仍由当前 Policy 和程序决定。

## 常设授权下的工作方式

项目所有者已授予常设授权。授权范围、条件和仍须逐次决定的事项以
[AGENTS.md「常设授权」](../../AGENTS.md#常设授权)为唯一权威，本节只说明流程。

1. **一次授权推进目标**：所有者决定目标与风险边界后，Agent 可自主拆分任务、选择技术方案、
   修复并验证；授权文件、门禁阈值、ASK 方向和 AGENTS.md 列出的高风险事项仍由所有者决定。
2. **task-free 改动端到端执行**：建分支 → 实现与本地检查 → 按常设授权推送并开 PR →
   启用 auto-merge，required check 通过后以 merge commit 合并 → 删除已合并分支。
   常设授权覆盖的本仓常规交付不因其外部性单独创建 task，也不逐次记录 push/merge action；
   执行前仍核对目标、版本、条件、已有禁令和目标仓规则。
3. **升级清单内的 task**：独立审核者必须是不同于实现者的另一个 Agent。按 AGENTS.md
   分别核对 spec、code 和本地 action 的代签条件；规格经独立设计审核通过后可先记录批准，
   不要求最终 `verify` 已完成。适用 verify 和独立实现审核通过后记录 code 批准，随后
   运行 Gate；按任务与目标仓规则推送并开 PR，required check 通过后合并。
   代签理由注明“常设授权”；actor 标签不证明所有者亲自审核。
4. **Policy 自失效的条件式预授权**：修改 Policy 的任务会让自身既有批准因绑定变化失效。
   可在 spec 中预先写明条件——spec 摘要不变、独立审核 APPROVE、route 未降低；三项同时
   满足且符合 AGENTS.md 中相应批准类型的全部条件时才可按常设授权重新记录批准；不能
   因预授权跳过验证、适用 CLI 或须由所有者作出的决定。
5. **例外上报**：重复 REQUEST_CHANGES 时保留发现并继续修复和独立复审；需要改变目标、
   接受未解决风险、超出授权或无法推进且需要决定时，暂停相关工作并集中上报。CI 未通过
   不得合并；其他独立工作继续。
6. **收尾只发摘要**：其余情况完成后一次性报告改动、验证、PR 与合并结果及未决事项；过程
   留在 CLI 账本与 PR 描述，不在 `docs/` 新增按日期的过程记录。

## 日常执行

1. 读取任务相关文件，确认范围与已有改动。按 [AGENTS.md](../../AGENTS.md) 的升级清单
   决定是否进入 AI Flow；进入清单要求有 task，不代表所有 task 都必定是 REVIEW。
   按真实事实分类，不为获得 AUTO 改写风险描述。
2. 适用 task-free 例外的工作直接实现、检查、小步提交。需要 AI Flow 的工作由 Agent
   完成事实录入、规格、分类、冻结和当前状态允许的推进；不要把这些机械步骤逐项交给人类。
3. 在已授权范围内持续修复并完成验证。命令拒绝后先保留现场并按 CLI 和
   [恢复指南](recovery.md)诊断；能在现有范围和权限内完成的恢复由 Agent 继续执行。
   新风险、范围或 Policy 变化仍按规则升级，不能为继续工作跳过拒绝。
4. 阶段提交服务于可恢复的实现结果，不要求每条账本事件各占一个提交。
   只包含当前阶段的相关改动，并保持账本、证据与日志追加式。进入验证后按照绑定语义处理
   subject 与账本提交；不得任意改写版本事实以节省一次验证。
5. 到达需要人类的决定点时，先完成当前允许完成的材料与检查，再提交一个具体问题。
   已授权且依然有效的决定不重复询问；任务尚能自主推进时不以“是否继续”结束。

### 控制交付范围

先明确用户能观察的结果、必要约束与非目标，并查找已有能力。较大改动在实施前核对
受影响的消费者、必需检查及验收环境是否可用；不可用时说明具体阻塞，继续不依赖该
条件的工作。普通任务不因此要求额外文档或审批；已明确的需求、质量门禁与授权仍须满足。

同一工作链中可独立发布且会推进 `main` 的变更，宜先完成，再从最新 `main` 创建并冻结
受治理任务；其他独立工作仍可并行。其他工作也可能推进 `main`，遇到基线漂移时保留原证据，
按现有 CLI、范围和分支规则处理，不为消除差异而机械扩大范围或假定冻结事实不变。

例如，修复一个测试误判时，应处理导致误判的原因，并核对依赖该结果的消费者；发现
与交付无直接关系的未来平台需求时，记录为后续事项，不将通用平台建设变成修复的前置
条件。若方案的成本或前提超出目标，比较更简单方案及保障差异；在已授权目标和风险边界内
由 Agent 选择，并按 CLI 更新规格、重新分类及审核。改变目标或接受未解决风险时由所有者
决定；不把未验证的方案称为等价。

### 新分类的风险输入

start 创建的是待完善草稿，不代表风险已经评估。新分类前，Agent 必须按实际变更显式
填写每个 DU 的 `impact_categories` 和 `controlled_actions`；只有确认没有对应风险时
才能写空数组。缺项会列出 DU 与字段并零写拒绝，不自动创建 ASK 或规格审核请求，
也不要求用户为补字段再批准一次。类型错误、未知动作枚举或重复项同样不能通过。

`controlled_actions` 仅接受 `production_data_delete`、`deploy`，可以同时列出；它是
风险分类事实，不是执行授权。原 `planned_actions` 保留可读计划及已知精确风险 token
的正向匹配，空的受控数组不能压掉这些风险。系统不从自然语言猜测真实命令；Agent
仍须核对计划与实际操作，不能把填表正确说成任意 shell 动作已经安全。

历史 task 的契约读取不强制迁移，已有分类只在原 Policy/input/base/subject 完全相同
时可 no-op 重放。Policy 或风险事实变化后的实际重分类必须补齐字段并按当前绑定推进；
不重写旧批准、证据或已关闭任务来消除历史 stale 提示。

### 动作检查不是执行授权

pre-command 仅在 Policy 明列时允许 `read` 类别；未知类别默认拒绝，不解析任务、不写
观察，也不要求用一条 action 批准换取放行。六项已知高风险类别保留原观察与拒绝路径。
任何通用本地批准都不让 wrapper 执行动作；定向 mutation 继续使用其独立受控消费流程。
真实 push/merge 按常设授权执行，授权之外的高风险动作仍需单独授权；可信执行边界的
限制见 [Hooks](hooks.md)。

## 什么才需要人类

`aiflow status TASK-ID` 的 `Missing:` 是待完成条件，不是“请用户批准”清单。
例如 `begin`、`implementation_result`、`verification_result` 和 `reverification`
本身都不是人类决定。`status` 是只读摘要，合并就绪和所需批准的最终判断用
`aiflow gate TASK-ID`；摘要与 Gate 冲突时先调查程序或绑定差异，不要求人类重复签字来
消除显示问题。

人工请求只在实际缺少业务方向、常设授权无法覆盖的 spec/code 决定或具体外部/高风险动作
授权时提出。
请求中说明缺少哪一项、为什么必须由人决定、推荐结论及其影响，并链接到最小充分材料。
同一时间可以决定的相关事项一起展示，但分别记录所需授权类型及其绑定；尚未完成的代码
审核不能提前批准。设计审核完成前不得跨过 CLI 的实现门。

普通实现方案、文件命名、测试执行和授权范围内的本地修复由 Agent 决定。独立 Agent
可以审核技术细节；CLI 要求的 ASK 业务方向选择和常设授权之外的风险接受仍由人类作出。通过测试、技术审核或
Gate 本身不构成授权：push、merge 按常设授权执行，deploy 等动作仍需各自授权。

已授权目标内可自主准备工具与公开依赖、在可丢弃隔离环境运行检查及受控变异，按目标仓
规则推进已授权接入；既有任务禁令、用户限制和未授权的私有材料传输边界仍有效。技术方案
不等于业务方向，须如实录入业务事实；CLI 已要求 ASK 时不得以 Agent 判断冒充用户回答。
批准因绑定变化失效后按当前事实核对；满足相应代签条件时重新记录，不复用失效记录。

### ASK 与 REVIEW 同时命中

同一决策单元可能既有多个实质方向需要选择（ASK），又涉及必须审核的变更（REVIEW）。
最终 route 仍为 REVIEW，但 matched_rules 中的 ASK 义务不能被覆盖：任务先等待方向回答，
回答后进入规格审核；回答不代替 spec/code 批准。Gate 按实际需要 ASK 的决策单元检查回答，
其他单元的回答不能代替它。BLOCK 仍优先，多个需要 ASK 的单元仍按现有明确错误拒绝。

重分类在同级或更低路由丢失 ASK 义务时，继续受降级门限制；升到更高路由（包括 BLOCK）
保留既有升级处理。非法持久分类由现有契约拒绝，不通过补写历史规则或默认为无需回答来恢复。
这项修复保留必要的人类方向决定，不代表增加日常机械步骤的人工确认，也不能据此宣称
人工成本已降低；效果仍按下述基线观察。

## 复算开销

在仓库环境中运行只读报告：

```sh
python tools/analysis/approval_overhead.py --format text
python tools/analysis/approval_overhead.py --format json
```

报告只读取现有账本，不创建 task、不重算路由、不写批准，也不触发外部动作。当前
classification 的路由分布是快照，不能当作每个历史时刻的分流结果。

本次修改前的可重放基线为 `1f28583`：42 个 task（AUTO 9 / ASK 1 / REVIEW 32），
119 条批准记录（首条 68、后续 51），1072 条事件，其中升级 33、验证失败 29。
按下述类型绑定口径，相同绑定后续记录为 spec 11、code 0、action 0。后续运行会包含
新增 task；比较时固定提交和统计口径，不能把数量自然增长当作改善或退步。

“后续批准”按同一 `(task, decision_unit, approval_type)` 的首条之后记录计数；
“相同绑定的后续批准”进一步比较该类型的绑定事实。这两个计数都不是“不必要批准”的
证明：规格、证据或授权消耗可能确实要求再次批准，尤其 action 不能只按哈希相同判冗余。
账本中的 actor 也不证明聊天中真的发生过一次人类打断。

评估一个改动是否有效，应在相同任务类型和观察窗口下比较：

| 指标 | 当前可得性与用途 |
|---|---|
| 任务数、路由、批准及后续批准、失败/升级事件 | 报告可复算，用于定位放大来源；不是人工成本本身 |
| 人类被打断次数、决定/审核用时 | 现有账本缺少可靠记录；标为 unavailable，不用批准条数代替 |
| 返工、缺陷逃逸及恢复代价 | 验证失败事件只反映一部分；不能从测试数量推断生产缺陷率 |
| 当前测试、覆盖率、静态检查 | 验证改动的工程质量，门槛与 CI 保持一致 |

后续有真实任务数据时，再记录同一目标因何打断人类、是否已有有效决定、花费时间和交付后
发现的缺陷；在数据出现前不宣称人工成本已经下降某个百分比，也不为收集指标添加逐次批准。

可重放的交付后基线、未知值口径及轻量观察方法见[低干预效果基线](effect-observations.md)。
它不增加逐次填报或审批，不采集原始会话入库，也不代表后台监控已经启动。

## 本次定位到的具体问题

历史[审批开销报告](../superpowers/plans/2026-09-03-approval-overhead-and-open-task-consolidation-directory.md)
记录了 38 个 task、113 条批准和 48 条后续批准。这是旧基线，不是当前统计。
其中的说明文字错误确实造成额外请求，但“审批开销只来自一份文档”的结论超出了证据：
任务自举范围、机械步骤间的等待与状态摘要的错误也需要分别检查。

历史上 `status` 曾因旧的 spec/code 批准失效而误报 stale，即使新的有效批准已覆盖所需
审核单元。该状态投影问题已修复：按当前所需单元和批准类型判断有效覆盖，同时保留历史
记录；status/Gate 对照有回归验证。若两者再次出现冲突，仍须按实际绑定诊断，不要求人类
重复批准来消除显示问题。阶段完成统计也不能作为真实可靠度目标已经达成的证据。
