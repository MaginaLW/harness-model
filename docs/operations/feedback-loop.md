# 任务收尾反馈闭环

本闭环由 Agent 在 ZCode 的每次真实任务收尾时执行：收集目标项目反馈，改进本仓方法，
再按目标项目规则回灌，并由下一次自然发生的真实任务检验。所有者已决定为
[明确登记的试点](adoption.md#已登记的外仓试点)统一采用本方法，当前为 `ai-agent-dotfiles`
和 `r3s-VPS`；新增项目须由所有者明确登记，不能自动扩展到其他仓库。

这是一条明确读取后遵循的工作约定，不是产品完成事件 API、工具 Hook、定时任务或
后台同步服务。可以在同一次 ZCode 运行中完成，但 Agent 必须显式读取目标项目入口、
本指南及将修改的仓库规则；仅存在文件不表示已加载。既没有新反馈、也没有适用版本差异时无改动，
不为维持循环新建业务任务、制造修订或重复运行历史检查。

## 首次接入及各项目状态

先在目标项目当前任务结束、相关写入权交还后，执行[首次接入提示词](../../examples/adoption/zcode-feedback-loop-prompt.md)。
目标 Agent 将精简的开始/收尾指针合入原有 `AGENTS.md` 和适合的接入文档，记录方法来源与
实际应用版本，并验证、提交。以后每次任务开始显式读取入口，收尾执行本指南，不依赖人类
每次重发提示词；这仍是 Agent 遵循约定，不是已实现的自动触发器。

本轮仅在 harness-model 准备统一方法与提示词，没有改写两个目标项目。各自首次持久化入口、
五项适用规则的回灌和运行确认仍待目标 Agent 执行；不能把本指南存在写成两个项目已经同步。
现有五项反馈来自 `ai-agent-dotfiles`，可以评估其方法是否适用于 `r3s-VPS`，但不能把该反馈
当作 `r3s-VPS` 也出现了同一缺陷的证据。各项目分别记录窗口、版本、结果与待处理项。

| 试点 | 复用的目标入口及验证边界 |
|---|---|
| `ai-agent-dotfiles` | 规则入口 `AGENTS.md`、接入说明 `docs/ZCODE.md`、权威状态 `STATUS.md` / 相关 `status/active/` 记录。文档修改按目标要求核对链接、差异和 secret scan；不启动 skill-management、live 同步或重写进行中的业务记录。 |
| `r3s-VPS` | 规则入口 `AGENTS.md`，复用 `README.md` 和 `docs/PROJECT_STATUS.md`；当前无 `docs/ZCODE.md`，不为统一名称另建一份。只同步本次修改的既有文档在 `tools/artifacts.manifest.json` 的 `localValidationArtifacts` 中对应哈希；最终按目标规则执行离线 Strict 和独立审查，回执放在既有树外位置，不为记 PASS 再改受检字节。 |

上述是接入映射，不代替目标仓最新规则。r3s 的清单适配只是维持既有文档完整性检查，
不得修改部署 artifacts、条目集合、Schema、检查发现范围或无关哈希。没有最后一次
文档/清单修改后的有效验证与独立审查，就保留未完成状态；闭环不触发远程检查或生产动作。

## 每次收尾怎样执行

1. **先完成当前任务。** 按目标项目原有规则完成已授权工作、验证和阶段提交，保留失败及
   未验证项。闭环不是跳过必需检查的收尾捷径。确认已处于明确的任务交接边界，其他 Agent
   或执行器已交还相关文件的写入权，再考虑改进与回灌；尚有并行写入时只整理反馈。
2. **在原处汇总反馈。** 使用目标项目原有权威收尾记录，追加本次真实窗口、来源提交、
   问题定位和可读取的脱敏证据指针；沿用[效果观察口径](effect-observations.md#下一批真实工作如何观察)。
   分清可复核、仅项目记载和缺失，明确版本、检查范围、耗时与预算及失败原因。
   历史材料缺失就记录缺失，不重跑来补造过去的成功或覆盖失败。
3. **筛选可泛化改进。** 对照既有反馈与当前[接入方法](adoption.md#真实任务的执行与收尾)，
   只处理已有证据支持、方向明确且在本轮授权范围内的问题。目标业务缺陷不直接改成本仓
   通用规则；重复问题引用已有结论，已解决问题不再造一份修订。涉及新方向或越界改动时，
   在原记录保留问题、理由和 `pending`，按适用规则请求必要决定，不阻塞无关的已授权工作。
4. **改进本仓。** 在已验证身份的本地 harness-model 检出中，重新读取其 `AGENTS.md` 和
   修改范围内规则，仅对 `docs/`、`examples/` 作最小完整修订。执行本仓要求的完整验证，
   包括覆盖率、差异覆盖率及静态检查，不以目标项目的通过结果代替。检查 diff 和暂存区，
   仅提交本次已复核改动，得到真实的本地 upstream 提交；未完成检查的修订不能记作已采纳。
   若检查依赖已提交的候选或文件清单，可先作已审阅的本地候选提交，再运行完整检查；
   通过前仍是未验证候选，不回灌、不推送，不为适配工作区状态改写测试条件。
5. **逐条回灌目标入口。** 回到目标项目，重新核对规则、身份、分支及写入边界。比较上次
   实际应用的 upstream 版本与本次已验证版本，只合并适用且缺失的文字到已经启用的
   `AGENTS.md` 和已选定的项目接入文档，在原有权威收尾记录追加版本、变更及限制。
   核对本次版本包含上次已应用版本且相关改进有验证依据；来源分叉、回退或验证不明时
   保留待核对状态，不自动选取任意 HEAD、不因版本号不同就重复应用。
   保留项目专有安全约束和已有等价条款，不整文件覆盖，不执行 Git merge。
   按目标项目当前规则执行验证、复核 diff 和暂存范围，再作本地提交；失败则保留待处理状态。
6. **下一真实任务再观察。** 回灌后不自动启动下一业务任务。下次正常工作显式读取更新
   后的入口，观察原问题是否再现、是否产生冲突、所需检查是否仍完整，结果再进入同一收尾
   流程。改了文本、测试通过或单次未再现均不是效果证明，不提前宣称阶段三验收或效率提升。

## 两个仓库的写入边界

每次跨仓库前，从已获准的本地项目定位信息找到检出，核实 Git 根目录、仓库身份、分支、
HEAD、worktree、工作区与暂存状态，以及本轮明确允许的文件。不要仅凭目录名、相邻路径或
旧记录认定身份；必要身份信息仅在本地核对，不把含凭据的 remote URL、机器名或绝对路径
写入记录。本指南不固定本机路径，不自动 clone、fetch、pull、切分支或建立新 worktree。

每个仓库都在写入前及提交前后重新检查以上状态。干净 HEAD 不能证明没有其他活跃写入者，
明确的任务边界和写入权交接仍是前提。发现其他活跃 writer、待改文件已脏、暂存区混有他人
改动，或基线/分支/范围发生无法解释的漂移时，停止该仓的闭环写入，保留 `pending` 与原因。
不 stash、reset、覆盖或顺手提交他人内容；无关修改也必须保留并与本次允许文件隔离。

如果产品权限不允许访问第二仓库、没有可信本地检出、身份无法核实，或无法确认安全交接，
在目标项目原有记录留下反馈和待应用的已知版本即可，不绕过沙箱或扩大权限。稍后获准且
条件满足的任务收尾可从这条记录接续，不把“待处理”误写成“已经同步”。
若目标记录本身也不可安全写入，则只在当前任务交接答复中说明 `pending` 和原因，不例外写入。

闭环授权只覆盖本仓文档/示例，以及登记目标项目的规则入口、必要接入文档和原有收尾记录，
另包含上表 r3s 既有文档条目的机械哈希同步；不包含源码、CI、`.ai`、技能、全局配置、
live 配置或后台采集。治理面、高风险和外部动作按各仓规则另行
处理，推送、合并、部署、删除、凭据导出和付费调用不在本闭环授权内。原质量门禁和审核
要求不能因“反馈优化”而降低；任何扩大推广对象或实现自动执行机制也须重新明确范围。

## 用既有记录去重和接续

每个反馈窗口在原有记录保留以下必要关联，可合为一段，不另建同步数据库、第二份权威
状态表或逐次必填报表：

- 来源项目的固定提交或观察窗口、问题位置及证据指针；同一窗口与同一问题只处理一次。
- 评估时的 upstream 基线、采纳/不采纳/待处理理由，以及本仓实际改进提交（若已产生）。
- 目标项目实际应用的 upstream 版本、适配范围、验证结果与尚未应用部分；仅部分完成就
  明示部分完成，不能将“本仓已提交”当作“目标已应用”。
- 后续真实任务的观察窗口及结果，引用原反馈；新证据更正用追加说明，不改写旧结论。

记录只能引用当时已存在的提交。目标应用提交尚未产生时，记录实际 upstream 版本与当时
目标基线即可；之后可引用实际提交，不要求一个提交预先写入自己的哈希。无新反馈时只检查
是否存在适用的待应用改进；也无版本差异则直接 no-op，不追加空洞的“已检查”记录。

当前首轮输入是[五项 ZCode 试点反馈](zcode-adoption-feedback.md)。该报告保存固定历史窗口；
是否已回灌、实际应用版本和后续效果应以目标项目真实收尾记录为准，本指南不预写完成结果。
