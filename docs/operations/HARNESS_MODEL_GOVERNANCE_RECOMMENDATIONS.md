# harness-model 仓库治理建议

## 1. 决策摘要与本次边界

先治理仓库，再决定是否恢复接入。治理的目标是让一个真实、已授权的小改动以更少的重复读取、材料准备和恢复轮次交付，同时守住质量、权限和证据真实性。

建议按以下顺序推进：

1. 暂停新增能力、平台化和现有接入重试，先确定维护对象、工作归属和保留边界。
2. 缩短默认阅读路径，合并当前状态的重复表述，保留原始历史的可追溯性。
3. 用已有失败找出最贵的重复步骤，把可确定的错误移到现有便宜检查边界。
4. 只修改已经证明需要共同变化的代码边界；没有实证收益的重构不实施。
5. 用自然任务验证成本下降，达标后结束治理，不把治理再扩成常驻平台。

**本次只交付建议和[执行计划](HARNESS_MODEL_GOVERNANCE_EXECUTION_PLAN.md)，没有执行上述修复。** 不运行 harness-model 的 task、探针、测试、LOCAL、CI 或 Gate；不恢复 Stage B；不修改其源码、Policy、任务账本、既有文档、工作树或历史。计划不是执行授权，也不改变现有批准规则。

用户本次“先治理、这次不执行 harness-model 内任务”的方向，优先于旧建议中的“先完成接入，再瘦身”。旧文档和失败记录保留，不能将新计划解释为取消安全要求或批准重试。

## 3. 根因判断：确认到什么程度

### 3.1 已有约束没有稳定落到工作方式

项目早已有简单实现、渐进读取、单一规则权威、共享完整 pytest 和低干预规则。继续增加一份原则文档不能解决执行偏差。应把“复用什么、删掉哪一步、何时停止”放进现有任务/PR 的验收说明，由交付结果证明。

当前状态页既有最新停止结论，也保留长篇逐窗口经过；读者容易把历史下一步当作当前指令。维护入口应只回答：当前候选、结果范围、真实阻塞、下一项获准动作。原窗口记录留在现有证据或历史可定位处，不另复制台账。

### 3.2 修改、历史整理和恢复被绑到同一条长链

小范围缺陷、版本漂移、材料绑定、独立审核、完整验证与关闭历史互相等待。更多 agent 无法消除共同基线和最终验收的串行依赖；同时重建环境还可能放大 I/O、安装和材料管理成本。

现有错误有明确的工程原因，也有仍 UNKNOWN 的原因。治理要缩短定位链，不能以“流程太重”为由跳过身份、材料、清理或真实覆盖率检查。

### 3.3 合同绑定范围可能大于实际失效范围

状态记录指出，目标 main 的协作条款和操作文档变化也触发激活前漂移停止。严格绑定保护证据真实性，但其成本需要按“哪个语义输入确实变了”解释。能在现行合同内证明不受影响的材料先复用；需要改变绑定契约时，作为单独提案审查，不能靠缓存、换 task 或换根绕过。

### 3.4 增量修补缺少退役出口

每次问题都容易留下一个 helper、材料副本、例外和说明。单项可能合理，累计会让后续任务读更多、核对更多。治理应让每项新增机制明确真实消费者、替代对象和退役条件；复用已有任务字段即可，不新建登记系统。

### 3.5 尚未证实，不能直接下结论

- 未取得可比的实际 token 用量，不能承诺节省百分比或把字符直接换算为 token。
- 未逐项证明重复全量验证频次，不能把14项检查说成14遍 pytest。
- 未证明所有大模块、测试或安全分支冗余，不按行数删代码。
- 未取得完整用户问答，不能把每条 project-owner 账本记录算作一次人工审批。
- 未独立复验最新交付源，不能把主根旧 WIP 的结构问题说成 source6 回归。

## 5. 代码治理只选可证明的一项

以下为待验证候选，不是已经批准的重构清单。以实际获准修改的交付基线重新定位，不能直接从脏主根整文件搬运。

1. **状态与门禁事实一致性。** 比较 `status_service.py` 的 `_current_facts`、`_approval_status`、`_merge_readiness` 与 `gate.py` 的 `evaluate_gate_facts`、`_v2_gate_facts`。若同一事实被重复推导且语义相同，让展示消费既有结果；用已有 `tests/integration/test_gate_parity.py` 扩展真实红例。只读性、错误与 stale 边界不同则不合并。
2. **材料采集与回放重复。** `verification_service.py` 已有一次记录、同产物消费机制。先定位调用方是否重复启动、绑定为何失效，不先造第二层缓存或重试框架。
3. **mutation 职责边界。** 大文件横跨动作消费、锁定、落盘和历史验证，可按一次真实故障的共同变化范围调整。单次消费、再校验和主树快照不能拆散成不完整路径；现有未提交拆分先保全，不预判它应该保留还是撤回。
4. **runner 保持不同契约。** 普通验证进程和受信 detector 生命周期拥有不同安全边界。只有调用 subprocess 这一共同点，不足以合并成通用执行器。

每项须写清：已复现问题、最小变化、被替代步骤、兼容范围、验证、回退。若不能说明净收益，结论写“不实施”，不是继续找理由抽象。

## 6. 成本与效果怎么验收

使用现有任务/PR 的短表记录，不新增监控服务、评分器或审计账本。最多选3个能清楚界定的样本：普通安全变更、治理面小修、一次真实失败恢复。历史样本只读复盘；新的自然任务只在另获授权后观察。

| 指标 | 基线与建议目标 | 防误读 |
|---|---|---|
| 默认阅读量 | 以同一任务的实际默认输入字符数为基线；建议减少至少50%，且关键信息查找通过。 | 可获实际 token 时记录实际值；字符只能作代理，不能宣称等额 token 节省。 |
| 重复工作 | 同一有效输入/产物/用途、没有失效原因的重复准备与验证降为0。 | 正式要求的不同阶段、不同候选验证不算无理由重复；不得豁免 required checks。 |
| 失败定位 | 被选中的已知失败能在昂贵完整轮前定位；失败输出至少有安全错误类别、操作和证据指针。 | 不公开原始私密响应，未知就报未知。 |
| 任务周转 | 可比自然小任务的主动处理时间建议下降至少30%；等待、测试、审核分别列出。 | 目标待基线确认，不是承诺；3个样本只支持小样本观察，不证明长期因果。 |
| 复杂度净增 | 本轮新后台服务/数据库/DSL/通用registry/新账本=0；每个新helper说明替代项。 | 必要安全修复允许净增；不要为达数量目标删除正确性。 |
| 质量与恢复 | 对应反例/正例、序列化/错误码兼容、完整适用验证、独立审核、回退演练全部满足。 | 任一高风险发现未关闭则不交付，不用成本收益掩盖。 |

若阶段一只完成了清理和测量，报告“基线/入口已改善，效果未验证”。没有可比样本时保持未知，不生成业务任务凑数字。

## 7. 防复发与终止条件

在现有实现审核里增加四个简短问题，不建立第二套门：当前需求是什么；已有能力为什么不够；新机制替代了什么；何时停止/退役。应优先复用标准库、平台能力和原有检查。

发生失败后先保存原件并回答“本轮新增了什么证据”。没有新证据不机械重跑、加超时、换根或开后继 task；需要改变风险、目标、预算或权限时才请求具体决定。仍在有效授权内且有明确诊断的必要修复，按现行规则完成，不人为设置按轮数自动停工。

治理收口需同时满足：版本与WIP不混淆；入口可定向查找；至少一个真实高成本点被消除或有证据判定不改；质量/权限边界保持；效果实测或明确未测；剩余项有保留/后置决定。完成后停止扩张，是否恢复接入由用户另行选择。
