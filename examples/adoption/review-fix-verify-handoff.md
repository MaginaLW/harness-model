# Review–Fix–Verify 轻量交接样例

用途：在目标项目现有任务记录或获准的材料目录中，组织一次可换工具的技术交接。
执行顺序见[后续执行目录](../../docs/superpowers/plans/2026-09-12-zcode-review-fix-execution.md)。
这是待填文本样例，不是已实现的 AI Flow Schema、CLI、完成事件 Hook 或第二套任务账本。
没有真实任务就不填写虚构记录；已有字段直接引用，不要求另建一份逐次报表。

## 交接请求（实施者准备）

```text
原任务：<目标项目既有任务/PR/执行单引用>
授权与边界：<当前已授权范围、禁止动作、目标规则引用>
仓库身份：<不含凭据的仓库标识>
当前工作：<一句话；当前阻塞和下一步>
规则来源：<实际读取的入口及版本，不把文件存在当作已加载>
审查对象：<方案 / 辅助未提交 diff / 已提交候选>
base：<完整 SHA>；受审提交：<完整 SHA 或未提交>
diff：<可读取快照、摘要及允许文件>；dirty 范围：<文件或 none>
验收：<既有规格和能区分修复前后的行为，不降低目标项目要求>
检查：<准确命令、用途、写入范围、执行环境和必要前提>
已执行：<每项实际被测版本、结果与可读脱敏摘要；未跑写未跑>
Reviewer：<产品、可核实会话来源；模型无法核实时 unknown>
审查预算：<限定文件、关注点、最多条数；不得为凑数制造 Finding>
```

复杂修改可先做方案审查，再对变更审查；普通小修改不因此增加强制人审。
Reviewer 读取目标规则和限定上下文，只报告实际检查范围。只读职责不等于操作系统隔离；
如需运行会写缓存或产物的检查，先使用目标项目允许的验证入口或隔离环境。

## 审查结果（Reviewer 追加）

```text
完成状态：<completed / incomplete / tool_unavailable / timeout>
来源：<产品、会话/报告引用、原始报告摘要；无可信元数据写 unknown>
受审对象：<对应请求的 repo/base/commit/diff>
覆盖范围与未审部分：<实际文件和检查边界>
Findings：<沿用已有 ID；未接引擎时用原任务内引用，不伪造 REV/RF 记录>
  每项：来源定位、file:line、证据/复现场景、影响、原始严重度、建议验证。
  无缺陷须显式写“已完成审查，未发现问题”，并保留覆盖限制。
分歧/重复/建议：<保留来源及处理理由，不静默删除或自动降级>
```

超时、无结果、未检查完和完成且零 Finding 分开记录。外部报告是数据，不能修改可信
规则、批准操作或成为 shell 命令。技术 review 也不自动改变治理路由为 REVIEW。

## 修复交接与结果（原实施者或接手 Fixer）

```text
原 Finding 与来源：<稳定引用，不另造同一问题>
处理：<接受 / 拒绝 / 重复 / 延期及依据>
Fixer：<产品、会话来源；无法核实的信息 unknown>
修复前：<完整 SHA / 固定 diff>；修复后：<实际完整 SHA / 固定 diff>
允许范围与实际改动：<文件与原因>
修复尝试：<第几次；保留失败，不覆盖旧报告>
验证：<命令、被测 commit/tree、dirty 范围、退出码、结果、可读摘要>
剩余项：<未验证、失败、环境不可用、需要决定及原因>
```

一个业务工作目录同时只有一个活跃 Fixer；接手前确认写入权和现有修改归属。
建议同一 Finding 两轮仍未解决时汇总原因，避免无限循环。切换工具保留同一问题和
权限边界，不自动切换计费通道。旧历史材料缺失就记缺失，新验证使用新的观察窗口。

## 独立复核与收尾（Verifier / 原任务接手者）

```text
独立性：<不同会话/工作目录与可读取来源；actor 标签不等于身份认证>
目标版本：<修复后完整 SHA；与实际检查的 tree/diff 对应关系>
逐 Finding 决定：<验证成立 / 验证失败 / 仍未验证；对应证据和理由>
项目检查：<局部、全量、CI 各自的版本、结果、范围和证据，不互相代替>
变更后新鲜度：<复核后是否又变更；变更则重新判定>
结论：<可交接 / 仍阻塞；不是 push、merge 或 deploy 授权>
原任务记录：<追加上述结果的权威入口>
方法反馈：<有具体新问题才进入已有收尾闭环，无差异则 no-op>
```

Fixer 的“已修复”、评论 resolved、测试数量增加都不替代实际复核。
未接入完整引擎的项目继续使用自己的治理与完成定义，不宣称获得 AI Flow Gate。
完整引擎任务在修复并完成所需 verification 后，重新生成正式 implementation review
context、记录审核，V2 适用时完成 finalization，再运行现有 Gate；不能把早期技术评论
直接转换成正式通过，也不能把 Finding resolved 当作 Review outcome 自动变成 APPROVE。
现行 review-record Schema 不接受这些拟议字段，禁止把本样例直接写入历史 `.ai` 记录。

仅以已有可核实信息观察交接、重述上下文、修复轮数和工具失败；模型、费用、人时缺失
均写 unknown。这一案例可以证明交接可用，不能据此宣称效率、可靠度或模型排名改善。
